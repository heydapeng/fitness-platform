# Fitness Platform — 数据库完整性加固设计 V3.6

## 1. 目的

V3.6 不增加新的产品能力，也不改变 Nutrition / Agent / RAG / Training 的业务边界。

本轮只解决四类数据库层风险：

1. **同一个用户字段与资源 ID 可以被错误拼接**：单列 FK 只保证 ID 存在，不能保证资源属于当前用户；
2. **Training Plan 的多级版本链可能串链**：`plan_id`、`plan_version_id`、`schedule_item_id` 单独都合法，但组合可能不合法；
3. **状态/来源字段允许语义矛盾组合**：例如 `FREE` Session 带 Schedule、User Custom Food 没有 owner；
4. **历史追溯信息不够强**：`business_date` 缺少生成时区来源，Approved RAG 文本仍可被原地修改。

设计原则仍保持：

- 已执行过的 Flyway migration 不修改，全部使用更高版本 forward-only migration；
- Service 仍是业务规则唯一入口；数据库约束是最后一道完整性防线；
- 不为了“数据库全能”引入大规模 Trigger/Stored Procedure；仅 RAG 的 Approved 内容冻结使用 Trigger，因为该规则直接保护历史引用语义；
- 不能由 MySQL 正确表达的跨行/动态规则明确留在 Java Service，不制造“看似已约束”的假象。

## 3. Nutrition / Core 加固

### 3.1 Food source 组合

V1.1 已经定义：

```text
SYSTEM
THIRD_PARTY
USER_CUSTOM
```

V3.6 将组合关系下沉为 CHECK：

| source_type | owner_user_id | source_provider | source_external_id |
| --- | --- | --- | --- |
| SYSTEM | NULL | NULL | NULL |
| THIRD_PARTY | NULL | NOT NULL | NOT NULL |
| USER_CUSTOM | NOT NULL | NULL | NULL |

这样可以阻止诸如：

```text
SYSTEM + owner_user_id = 123
USER_CUSTOM + owner_user_id = NULL
THIRD_PARTY + source_external_id = NULL
```

这些数据库层自相矛盾状态。

注意：**Food 可见性仍由 Service 负责。**

因为“公共 Food owner 为 NULL；自定义 Food owner 必须等于当前用户”是带 OR 的授权规则，普通 FK 不能同时表达“公共或本人”。所有 Food Search / Favorite / Record 写入仍必须校验：

```text
food.owner_user_id IS NULL
OR food.owner_user_id = currentUserId
```

### 3.2 Food Record / Group / Photo owner chain

原结构：

```text
food_record.user_id -> app_user
food_record.group_id -> food_record_group
```

这允许两个 FK 各自成立、但 `food_record.user_id != food_record_group.user_id`。

V3.6 增加：

```text
food_record_group UNIQUE(user_id, id)
food_record       UNIQUE(user_id, id)
```

并将关联改为：

```text
food_record(user_id, group_id)
    -> food_record_group(user_id, id)

food_photo(user_id, food_record_id)
    -> food_record(user_id, id)

food_photo(user_id, food_record_group_id)
    -> food_record_group(user_id, id)
```

因此后台脚本、误写 Repository 或未来批量导入都无法制造跨用户附件/分组。

复合 FK 使用 `ON DELETE RESTRICT`。原因是 MySQL 的复合 FK `SET NULL` 会尝试把 FK 中所有列置 NULL，而 `user_id` 必须非空。若未来提供 Group 物理删除，Service 应先显式解除 Record 关联；当前产品并不依赖 Group 物理删除。

### 3.3 business_date timezone provenance

新增：

```text
food_record.business_timezone_id
food_record_group.business_timezone_id
workout_session.business_timezone_id
```

语义：**保存生成当前 `business_date` 时使用的 IANA timezone。**

例如：

```text
occurred_at             2026-09-22 00:30:00 UTC
business_timezone_id    America/Los_Angeles
business_date           2026-09-21
```

字段在 migration 中保持 nullable，因为无法安全地根据用户“当前 timezone”推断历史记录当时使用的 timezone。对于 legacy row：

```text
NULL = historical timezone provenance unknown
```

对于 migration 之后的所有新增/合法编辑：

```text
business_timezone_id MUST be populated by Service
```

不要做批量“用当前 user.timezone_id 回填历史”的自动修复，除非业务确认用户从未修改过 timezone。

### 3.4 Nutrition Goal 并发

区间不重叠仍不适合用普通 UNIQUE 表达。

旧方案只写：

```text
SELECT nutrition_goal ... FOR UPDATE
```

当某用户当前不存在相关 Goal 行时，两个并发事务仍可能同时判断“无冲突”。

统一改为 per-user mutex：

```sql
BEGIN;

SELECT id
FROM app_user
WHERE id = :userId
FOR UPDATE;

SELECT id, effective_date, end_date
FROM nutrition_goal
WHERE user_id = :userId
FOR UPDATE;

-- Java Service 校验 overlap / 调整旧 end_date / 写新 Goal

COMMIT;
```

所有 Goal 写入口，包括 REST、Admin、AI Tool，必须走同一个 Domain Service。

## 4. AI 关系链加固

### 4.1 问题

原结构分别校验：

```text
agent_run.user_id         exists
agent_run.conversation_id exists
agent_run.user_message_id exists
```

因此数据库理论上允许：

```text
Agent Run 属于 User A / Conversation A
但 user_message_id 指向 Conversation B
```

Action Audit 也存在类似风险。

### 4.2 新约束

父级增加：

```text
ai_conversation UNIQUE(user_id, id)
ai_message      UNIQUE(conversation_id, id)
ai_agent_run    UNIQUE(user_id, conversation_id, id)
```

Agent Run 使用：

```text
(user_id, conversation_id)
    -> ai_conversation(user_id, id)

(conversation_id, user_message_id)
    -> ai_message(conversation_id, id)

(conversation_id, assistant_message_id)
    -> ai_message(conversation_id, id)
```

Action Audit 使用：

```text
(user_id, conversation_id)
    -> ai_conversation(user_id, id)

(user_id, conversation_id, agent_run_id)
    -> ai_agent_run(user_id, conversation_id, id)
```

因此 Trace/Audit 不再只是“几个 ID 都存在”，而是必须位于同一 owner + conversation chain。

### 4.3 为什么 Message FK 改为 RESTRICT

原单列 Message FK 使用 `ON DELETE SET NULL`。

复合 FK 如果 SET NULL，会连 `conversation_id` 一起置 NULL，与 NOT NULL 冲突。因此 V3.6 对物理删除采用 RESTRICT。

产品本来就使用 Conversation `status = DELETED` 表达用户删除/隐藏，不依赖物理删除 Message；Trace 的历史完整性优先级更高。

### 4.4 仍由 Service 校验

数据库没有进一步强制：

```text
user_message_id.role == USER
assistant_message_id.role == ASSISTANT
```

因为这是类型语义，不值得为此复制更多列或增加复杂 Trigger。Agent Service 创建 Run 时必须校验。

## 5. Training 加固

Training 是本轮变化最大的区域。

### 5.1 Exercise source

当前产品只有：

```text
SYSTEM
USER_CUSTOM
```

V3.6 增加：

```text
SYSTEM      -> owner_user_id IS NULL
USER_CUSTOM -> owner_user_id IS NOT NULL
```

与 Food 一样，使用自定义 Exercise 时仍必须由 Service 校验：

```text
exercise.owner_user_id IS NULL
OR exercise.owner_user_id = currentUserId
```

### 5.2 Current Plan Version

原设计：

```text
training_plan.current_version_no
```

它只是数字，不能直接 FK 到某一行版本。

V3.6 新增：

```text
training_plan.current_version_id
```

同时保留 `current_version_no` 作为显式 version number，并用一个复合 FK 绑定三者：

```text
training_plan(id, current_version_id, current_version_no)
    -> training_plan_version(plan_id, id, version_no)
```

约束：

```text
training_plan_version.version_no > 0
无正式版本： current_version_id IS NULL AND current_version_no = 0
有正式版本： current_version_id IS NOT NULL AND current_version_no > 0
```

这样既保留现有代码易读的 version_no，又让数据库证明“当前版本 ID 确实属于这个 Plan，且版本号匹配”。

创建新 Plan Version 的事务必须：

```text
INSERT training_plan_version
INSERT version children
UPDATE training_plan.current_version_id/current_version_no
COMMIT
```

### 5.3 Schedule Item locator

原约束只保证：

```text
cycle_day_no IS NOT NULL OR specific_date IS NOT NULL
```

无法阻止：

```text
DATE_SPECIFIC + cycle_day_no
REPEATING_CYCLE + specific_date
cycle_day_no > cycle_length_days
WEEKLY + cycle_length_days != 7
```

V3.6 在不可变 Schedule Item 保存：

```text
schedule_type_snapshot
cycle_length_days_snapshot
cycle_length_key_snapshot
```

其中 `cycle_length_key_snapshot` 只是 FK helper：

```text
NULL cycle length -> key 0
```

Plan Version 也有对应 `cycle_length_key`。复合 FK：

```text
(plan_version_id, schedule_type_snapshot, cycle_length_key_snapshot)
    -> training_plan_version(id, schedule_type, cycle_length_key)
```

因此 item 的 locator mode 与所属 Version 一致。

CHECK 再保证：

```text
DATE_SPECIFIC:
  specific_date NOT NULL
  cycle_day_no NULL
  cycle_length_days_snapshot NULL

REPEATING_CYCLE / WEEKLY:
  specific_date NULL
  cycle_day_no NOT NULL
  1 <= cycle_day_no <= cycle_length_days_snapshot

WEEKLY:
  cycle_length_days_snapshot = 7
```

### 5.4 Scheduled Workout 完整版本链

原来是四个相互独立的 FK：

```text
user_id
plan_id
plan_version_id
schedule_item_id
```

V3.6 改为：

```text
(user_id, plan_id)
    -> training_plan(user_id, id)

(plan_id, plan_version_id)
    -> training_plan_version(plan_id, id)

(plan_version_id, schedule_item_id)
    -> training_plan_schedule_item(plan_version_id, id)

(schedule_item_id, item_type)
    -> training_plan_schedule_item(id, item_type)
```

从而数据库保证：

```text
User
  ↓
Plan
  ↓
Plan Version
  ↓
Schedule Item
  ↓
Scheduled Workout
```

是一条真实链，而不是四个各自合法但互相无关的 ID。

### 5.5 Workout Session source

新增 `source_scheduled_item_type` 快照，并将 source 组合收紧为：

```text
FREE -> source_scheduled_workout_id IS NULL
        source_scheduled_item_type IS NULL

PLAN -> source_scheduled_workout_id IS NOT NULL
        source_scheduled_item_type = WORKOUT
```

再用：

```text
(user_id, source_scheduled_workout_id, source_scheduled_item_type)
    -> scheduled_workout(user_id, id, item_type)
```

因此既阻止 User A 的 Session 关联 User B 的 Calendar 投影，也阻止把 `REST` Scheduled Item 当成计划训练启动 Session。

### 5.6 一个 Schedule 对几个 Session

V3.6 **不改变**现有：

```text
UNIQUE(source_scheduled_workout_id)
```

因此当前明确语义是：

> 一条 Scheduled Workout 最多对应一条 Workout Session row。

PRD 没有定义“用户 Cancel 后是否允许为同一 Schedule 创建第二个 attempt”，所以本轮不擅自引入多 attempt。

当前实现建议：

- Cancel 后如果用户重新开始同一计划训练，复用/恢复原 Session row；
- 或产品后续明确需要 attempt history，再另做 migration，引入 `attempt_no` 或 active-only unique key。

不要在当前版本悄悄放开 UNIQUE，否则 Plan Completion 与“一个 Schedule 是否完成”的统计口径会变得不明确。

### 5.7 仍需 Service 保证的 Training invariant

以下跨层规则不建议继续堆 Trigger：

1. `source_routine_id` 必须是当前用户可见 Routine；
2. `training_plan_item_exercise.exercise_id` 必须是当前用户可见 Exercise；
3. `item_type = REST` 时不得创建 `training_plan_item_exercise`；
4. `workout_session_exercise.source_plan_item_exercise_id` 若存在，必须来自本 Session 对应 Schedule Item；
5. `workout_set.source_plan_set_target_id` 若存在，必须属于对应 source plan exercise；
6. Future 时间不得创建 COMPLETED Workout Session；
7. 历史事实一个月编辑窗口；
8. `business_timezone_id` 对所有新 Session 必填。

这些规则必须在 Training Domain Service 中形成集中 validator，并覆盖 REST / AI Tool / Batch 等所有入口。

## 6. RAG 版本完整性

### 6.1 一个 Document 只能有一个生产 Active Version

新增 generated guard：

```text
active_approved_document_id =
  document_id when APPROVED + ACTIVE
  NULL otherwise
```

并建立 UNIQUE：

```text
UNIQUE(active_approved_document_id)
```

MySQL UNIQUE 允许多个 NULL，因此：

- DRAFT / REVIEWING / INACTIVE / EXPIRED 可以存在多条；
- 同一个 Document 最多一个 `APPROVED + ACTIVE`。

同时 CHECK：

```text
effective_status = ACTIVE -> review_status = APPROVED
```

### 6.2 Approved 内容冻结

历史 `rag_retrieval_item.chunk_id` 的价值在于之后仍能说明：

> 当次回答到底用了哪段内容。

因此一旦 Version APPROVED：

禁止原地修改：

- Version document identity / version label / publish date / content hash / source object；
- Chunk 的 version、index、heading、topic、content、token count、content hash；
- 向 Approved Version 新增或删除 Chunk。

允许：

- Version `effective_status` 从 ACTIVE 变为 EXPIRED / INACTIVE；
- Chunk `vector_store` / `vector_ref` / `embedding_model` / `index_version` / `status` 更新，以便重新索引。

内容需要变化时必须创建新的 `knowledge_document_version`。

这一条使用数据库 Trigger 是刻意选择：它保护的是历史证据链，而不是普通业务计算逻辑。

## 7. 升级顺序

已有环境：

```text
1. 备份
2. 在生产相同 MySQL 小版本 clone/rehearsal
3. 执行 examples/V3_6_preflight_checks.sql
4. 修复所有非零结果
5. 部署兼容 V3.6 schema 的应用版本
6. flyway migrate
7. 执行 examples/V3_6_post_migration_checks.sql
8. 运行 Domain integration tests
```

特别注意：

- `business_timezone_id` legacy NULL 不应自动伪造；
- 新应用在 V3.6 后必须写 timezone provenance；
- 应用切换到 `current_version_id + current_version_no` 双字段更新；
- RAG 发布流程必须先完成 Chunk，再把 Version 置 APPROVED；Approved 后不能继续补 Chunk。

## 8. 必须新增的测试

### Nutrition

- User A Food Record 不能挂 User B Group；
- User A Photo 不能挂 User B Record/Group；
- SYSTEM / THIRD_PARTY / USER_CUSTOM 非法 source 组合写入失败；
- 两个线程同时创建重叠 Goal，最多一个事务成功进入冲突校验后的写入路径；
- 新 Food Record 写入 timezone provenance。

### AI

- Agent Run 不能引用其他用户 Conversation；
- Agent Run 不能引用另一个 Conversation 的 Message；
- Action Audit 不能引用其他 Conversation/User 的 Agent Run。

### Training

- current version ID/number 与 Plan 不一致时写入失败；
- Schedule Item locator 与 Version schedule type 不一致时失败；
- cycle day 超过 cycle length 时失败；
- Scheduled Workout 串用其他 Plan Version / Schedule Item 时失败；
- FREE + Schedule、PLAN + NULL Schedule、PLAN 指向 REST Schedule 均失败；
- User A Session 不能关联 User B Schedule。

### RAG

- 同 Document 第二个 APPROVED+ACTIVE Version 失败；
- ACTIVE 但非 APPROVED 失败；
- Approved Version 身份/内容元数据修改失败；
- Approved Chunk text 修改/新增/删除失败；
- Approved Chunk vector index metadata 更新成功；
- ACTIVE -> EXPIRED 成功。

## 9. 本轮刻意不做

以下不是 V3.6 必需修改：

- 不建立 Nutrition / Training summary fact 表；
- 不把 `secondary_muscles_json` 强行拆表：PRD 尚未明确 MuscleGroup 是否需要 secondary muscle 参与筛选，等 V3.5 查询语义最终确认后再做；
- 不为 public-or-user-owned Food/Exercise 引入复杂授权 Trigger；
- 不新增 AI Draft 业务事实表；
- 不改变 Scheduled Workout 的单 Session 语义；
- 不对 RPE/RIR 自行定义 PRD 未规定的数值区间。

这几项继续保持“需求明确后再迁移”，避免数据库设计反过来替产品做决定。
