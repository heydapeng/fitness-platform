# Fitness Platform — 分阶段数据库演进设计

本文说明 V1 之后每个产品阶段的数据库增量。核心原则是：**业务事实表保持稳定，版本升级尽量新增表/列/索引，不重建既有事实语义。**

---

## 1. 版本与 Flyway 对应关系

| 产品版本 | Flyway 前缀 | 数据库变化 |
| --- | --- | --- |
| V1 | `V1_0_x` | User / Food / Goal / Food Record / Idempotency |
| V1.1 | `V1_1_x` | Third-party Food、Custom Food、Alias、Favorite、Food Record Group |
| V1.2 | `V1_2_x` | Food Photo、Export Job；Analytics 不另建事实表 |
| V2 | `V2_0_x` | AI Conversation、Message、Agent/Tool Trace、Action Audit |
| V2.1 | `V2_1_x` | Knowledge metadata/chunk、RAG Trace；向量留在 Vector Store |
| V3 | `V3_0_x` | Exercise、Routine、Plan Version、Schedule、Workout Session/Set |
| V3.5 | `V3_5_x` | 统计索引；首期不新建统计事实表 |
| V4 | 无强制 schema migration | AI Training 复用 V2 + V3 表和 Service |
| Future | 待核心留存验证后 | Share / Body / Coach / Health 等独立迁移 |

## 2. V1.1：快速记录与食品搜索

### 2.1 Food 外部来源与自定义食品

对 `food` 增量增加：

- `owner_user_id`：自定义 Food 的用户所有者；公共 Food 为 NULL；
- `source_provider`；
- `source_external_id`；
- `source_updated_at`；
- `barcode`。

核心唯一键：

```text
(source_provider, source_external_id)
```

用来保证同一第三方 Food 不会反复沉淀为多条本地记录。

`source_type` 的业务枚举为：

- `SYSTEM`
- `THIRD_PARTY`
- `USER_CUSTOM`

V3.6 起，这三个值以及 `source_type / owner_user_id / source_provider / source_external_id` 的组合关系同时由数据库 CHECK 兜底；Service 仍负责可见性和写入校验。

查询可见 Food 时:

```text
公共 Food: owner_user_id IS NULL
+ 当前用户 Food: owner_user_id = currentUserId
```

不要让普通用户通过传入 ownerId 查询别人的 Custom Food。

### 2.2 `food_alias`

用于 name/brand 之外的搜索别名。Alias 只是搜索入口，不改变营养事实。

### 2.3 `user_food_favorite`

唯一 `(user_id, food_id)`，不需要在 Food 表增加 favorite count 作为权威字段。

### 2.4 最近吃过 / 常吃

首期不建新表，直接从 `food_record` 计算：

```sql
-- 最近使用
SELECT food_id, MAX(occurred_at) AS last_used_at
FROM food_record
WHERE user_id = :userId
  AND deleted_at IS NULL
GROUP BY food_id
ORDER BY last_used_at DESC;
```

```sql
-- 近 30 天常吃
SELECT food_id, COUNT(*) AS use_count, MAX(occurred_at) AS last_used_at
FROM food_record
WHERE user_id = :userId
  AND business_date >= :startDate
  AND deleted_at IS NULL
GROUP BY food_id
ORDER BY use_count DESC, last_used_at DESC;
```

热点结果可以放 Redis，但 Redis 不作为事实源。

### 2.5 多食品一次添加

增加 `food_record_group` + `food_record.group_id`。

注意：每个 Food 仍然是独立 `food_record`；Group 只是组织层。

一次 batch：

```text
BEGIN
→ Claim batch requestId
→ 校验全部 Food/amount/time
→ INSERT food_record_group
→ INSERT N 条 food_record
→ idempotency SUCCEEDED，response 保存 N 个 recordId
COMMIT
```

保证全批成功或全批失败。

## 3. V1.2：图片、Analytics、导出

### 3.1 Food Photo

新增 `food_photo`，只保存对象存储 metadata，不把二进制图片放 MySQL。

图片必须二选一关联：

- 单条 `food_record`；
- 一个 `food_record_group`。

图片上传失败不回滚已成功的 Food Record。

推荐流程：

```text
Food Record transaction commit
→ 创建/取得 photo upload metadata
→ 上传对象存储
→ READY / FAILED
```

### 3.2 Analytics 不创建“统计事实表”

V1.2 首期 Dashboard/Analytics 都直接基于 `food_record` snapshot/actual 字段聚合。

`QuerySpec` 是 Java 业务查询 DTO，而不是数据库实体；只有 Export Job 为了复现查询才把它保存到 `query_spec_json`。

这样能保证：

```text
Same QuerySpec
→ Dashboard/Analytics Service
→ Table
→ Export
→ V2 AI Query
```

### 3.3 Export Job

`export_job` 保存：

- scope；
- domain；
- format；
- QuerySpec JSON；
- include photos；
- processing status；
- 对象存储结果；
- expires_at；
- error 信息。

导出文件本身不放 MySQL。

## 4. V2：Fitness Agent Core

PRD 明确要求：AI 不直接写表，所有正式写操作仍然走 V1/V1.1 Service。

### 4.1 Redis 与 MySQL 的职责边界

**Redis：**

- conversation summary；
- 最近实体引用；
- 最近 Query context；
- Pending Action 完整 resolved payload；
- 短期 Tool result summary。

**MySQL：**

- 用户可见的 Conversation/Message 历史；
- Agent Run trace；
- Tool Call trace；
- Action 生命周期审计；
- 最终业务事实仍写原 Food Record 等业务表。

### 4.2 `ai_conversation` / `ai_message`

用于独立 AI 页的“最近会话”和用户可见聊天历史。

短期 Memory 不等于消息历史。事实查询仍必须回到业务 Service。

### 4.3 `ai_agent_run` / `ai_tool_call`

把一次请求关联成：

```text
conversationId
→ messageId
→ agentRunId
→ toolCallId
→ actionId
→ requestId
→ resourceId
```

Trace 里禁止记录 JWT、密码、API Secret；request/response JSON 应是脱敏后的结构化信息。

### 4.4 `ai_action_audit`

持久化状态：

```text
PARSED
→ RESOLVING
→ READY_FOR_CONFIRMATION
→ CONFIRMED
→ EXECUTING
→ SUCCEEDED / FAILED / CANCELLED
```

但等待确认时真正可执行的 resolved params 按 PRD 放 Redis，确认接口根据 `actionId` 从服务器端 Pending Action 读取，不信任前端重新提交一套任意参数。

正式写入仍使用 `idempotency_request`。

## 5. V2.1：RAG

### 5.1 MySQL 不存向量作为核心方案

PRD 已明确 Vector Store 技术可以独立选择。因此 MySQL 负责：

- Document identity；
- Document Version；
- 审核/有效状态；
- Chunk 文本和 metadata；
- Vector Store reference；
- Retrieval/Rerank trace。

Embedding 向量存 Vector DB / pgvector / 独立向量服务。

### 5.2 文档版本

`knowledge_document` 是稳定逻辑身份；`knowledge_document_version` 保留版本。

正式检索只允许：

```text
review_status = APPROVED
AND effective_status = ACTIVE
```

旧版本不物理删除，标记 EXPIRED/INACTIVE，使历史 Trace 仍能知道当时使用了哪个版本。

V3.6 起数据库额外保证：同一个逻辑 Document 最多只有一个 `APPROVED + ACTIVE` 版本；版本一旦 APPROVED，其身份/内容元数据与 Chunk 文本冻结，只允许更新向量索引指针、index version 和有效状态。内容变化必须创建新 Version。

### 5.3 Chunk

`knowledge_chunk` 记录：

- document version；
- chunk index；
- heading/topic；
- content；
- vector_ref；
- embedding_model；
- index_version。

当 embedding model 切换时，可以重建 Vector Store 并更新 `vector_ref/index_version`，无需改业务事实表。

## 6. V3：训练闭环与 Calendar

V3 的关键不是“表多”，而是严格分开**计划**和**实际事实**。

### 6.1 Exercise

`exercise` 当前定义支持：

- 中/英文名；
- muscle/equipment/category；
- user custom；
- status；
- `tracking_type`；
- `load_volume_applicable`。

最后两个字段是为了 V3.5 避免把跑步、duration、自重等错误混算为 Load Volume。

### 6.2 Routine

`workout_routine` 是可编辑模板。

当 Routine 被加入 Plan Version 时，不让 Plan 直接依赖 Routine 的“当前可变内容”，而是把 Exercise/Set targets 复制到不可变 `training_plan_*` version 表。

因此后来改 Routine 不会改写历史计划语义。

### 6.3 Plan Version

结构：

```text
training_plan                 稳定计划身份/当前状态（current_version_id 指向当前不可变版本）
  └─ training_plan_version    每次重大编辑生成新版本
       └─ training_plan_schedule_item
            └─ training_plan_item_exercise
                 └─ training_plan_item_set_target
```

支持：

- REPEATING_CYCLE；
- WEEKLY；
- DATE_SPECIFIC；
- 任意 N 天循环；
- Rest Day；
- 多计划并行。

### 6.4 Scheduled Workout

`scheduled_workout` 是 Plan Version 在 Calendar 某天的投影。

它引用不可变：

- `plan_version_id`；
- `schedule_item_id`。

Plan 更新后，未来新投影使用新版本，历史投影继续引用旧版本。

V3.6 起 `scheduled_workout` 使用复合 FK 强制 `user → plan → plan_version → schedule_item` 属于同一条链，同时校验 `item_type` 与来源 Schedule Item 一致，避免多个合法 ID 被错误拼成一条非法投影。

Missed Schedule 不通过数据库任务自动平移日期。

### 6.5 Workout Session / Set

实际事实：

```text
workout_session
  └─ workout_session_exercise
       └─ workout_set
```

自由训练：`source_scheduled_workout_id = NULL`。

计划训练：必须关联 WORKOUT 类型的 Schedule；V3.6 起数据库 CHECK 强制 `FREE + NULL` / `PLAN + WORKOUT Schedule` 的组合，并通过 `(user_id, source_scheduled_workout_id, source_scheduled_item_type)` 复合 FK 防止跨用户或误关联 REST。实际 Sets 仍独立保存，不能用 Plan targets 覆盖。

`workout_session_exercise` 再次 snapshot Exercise 的名称、muscle/category、tracking_type 等，防止 Exercise 后续修改改变历史统计。

## 7. V3.5：训练统计

首期不增加 `training_daily_summary`、`exercise_pr_cache` 等派生事实表。

原因：

- 当前数据量早期可直接从 Session/Set 聚合；
- 用户一个月内可修改历史 Set；
- 过早做缓存表会引入“事实已改、聚合没同步”的一致性问题。

V3.5 migration 首先只增加必要索引。

当真实数据量证明查询瓶颈后，再引入：

- materialized summary；
- async recompute；
- cache version；
- event/outbox。

这些应由性能数据驱动，而不是 PRD 首版提前复杂化。

## 7.6 V3.6：关系完整性加固

V3.6 不新增产品功能，专门把此前主要依赖 Service 的关键关系收紧到数据库层：

- Nutrition：Food source 组合约束；Food Record/Group/Photo 复合 owner FK；记录写入 timezone provenance；
- AI：Agent Run / Message / Action Audit 必须属于同一 user + conversation chain；
- Training：`current_version_id`、Plan/Version/Item 复合 FK、Schedule locator 强约束、Workout Session source 组合约束；
- RAG：每 Document 最多一个 APPROVED+ACTIVE Version；Approved Version/Chunk 文本冻结。

仍然留在 Service 的规则包括：Goal 区间非重叠的 per-user 事务锁、公共/自定义 Food 与 Exercise 的可见性、REST Item 不能带 exercise、计划来源 Exercise/Set provenance 的跨层校验、未来已完成 Session 禁止创建、一个月编辑窗口。详见 `docs/03_数据库完整性加固_V3.6.md`。

## 8. V4：AI Training Extension

V4 首期**不需要新增核心表**。

原因：

- Training Read Tool 读取 V3/V3.5；
- Workout Draft / Plan Draft 使用 V2 Pending Action；
- Preview/Confirm 使用 `ai_action_audit` + Redis；
- Confirm 后调用 V3 Workout/Plan Service；
- Trace 复用 `ai_agent_run` / `ai_tool_call`；
- Export 复用 `export_job`。

如果未来要长期保存“用户未确认的 AI Draft 版本历史”，再增加专门 Draft 表；当前 PRD 没有要求，不应提前建。

## 9. Future

Future 功能应独立迁移，不反向污染核心表。

建议未来候选：

### Share

```text
share_link
- user_id
- resource_type (WORKOUT / PLAN)
- resource_id
- token_hash
- visibility
- settings_json
- expires_at
- revoked_at
```

分享 token 只保存 hash，不保存可直接访问的明文 token。

### Body Metrics

若只先做体重，可建轻量：

```text
body_metric
- user_id
- occurred_at
- business_date
- weight_kg
- body_fat_pct nullable
- note
```

无需提前建立复杂完整 Body Domain。

Coach / Health Integration 在真实产品排期确定后再建关系/授权表。

## 10. 迁移策略总结

数据库稳定性依赖以下顺序：

```text
V1    先把 Nutrition Fact 做正确
V1.1 只增强 Search / Quick Logging
V1.2 在同一事实之上做 Analytics / Attachment / Export
V2    AI 变成业务入口，不另建业务事实
V2.1  Knowledge 与 Personal Facts 分离
V3    新增 Training Fact + Versioned Plan
V3.5  从原始 Training Fact 统计
V4    AI 复用 Training Service
```

最重要的边界：

- `food` / `exercise` 是可变定义；
- `food_record` / `workout_session` 是历史事实；
- `nutrition_goal` / `training_plan` 是比较基准/未来计划；
- AI/RAG 不能成为业务事实的第二来源。
