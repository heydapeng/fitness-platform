# Fitness Platform 全周期开发任务与验收清单

> 执行方式：学习者独立编码，完成任意一个任务后提交验收。  
> 核心毕业线：M0 - M11（对应简历中的 Fitness Agent + RAG）。  
> 完整产品线：M0 - M15（增加训练、训练统计和 AI Training）。  
> Future：M16，仅在核心产品稳定后选择。

## 1. 验收合作方式

### 1.1 每次提交验收时提供

```text
任务编号：例如 T3.4
完成内容：用自己的话概括
改动文件：列出文件
验证方式：运行了哪些测试/请求
测试结果：成功输出或失败现象
仍有疑问：可选
```

代码已经在共享工作区时无需粘贴全部代码，只需告诉我任务编号。我会检查：业务正确性、分层、命名、异常、权限、事务、测试和与文档的一致性。

### 1.2 通过等级

| 结论 | 含义 |
| --- | --- |
| PASS | 满足当前任务，可进入下一项 |
| PASS WITH NOTES | 功能正确，有不阻塞后续的小改进 |
| CHANGES REQUIRED | 存在业务、设计或测试缺口，修正后复验 |
| BLOCKED | 前置条件或环境未解决，先处理阻塞项 |

### 1.3 完成定义 Definition of Done

一项任务只有同时满足以下条件才算完成：

- 项目能够编译；
- 相关自动化测试通过；
- 没有破坏已有测试；
- 正常、异常和权限路径都有证据；
- DTO/错误码/API 与接口契约一致；
- 没有提交密码、Token、Secret、构建产物；
- 新业务规则有测试或明确的验证方式；
- 能用自己的话解释实现原因。

# M0 工程基线

目标：任何开发者按 README 可以在干净环境中构建、测试和启动项目。此阶段不新增业务功能。

## T0.1 保护现有工作并建立提交基线

任务：检查当前 `git status`，区分已有改动、移动目录和新文件；整理为语义明确的提交，不删除自己无法解释的代码。

验收：

- 工作区变更有明确归属；
- `.gitignore` 覆盖 IDE、密钥、本地数据库、`target`、`node_modules`、导出物；
- 不包含真实数据库密码和 JWT Secret；
- 能解释每个未提交文件为何保留。

## T0.2 固化 Java 与 Maven 环境

任务：为后端增加 Maven Wrapper，README 声明 Java 21，确保命令不依赖机器全局 Maven。

验收：新终端中 `java -version`、Wrapper 版本和 `./mvnw test` 证据；Windows 路径可用；不把本地 Maven 仓库提交 Git。

## T0.3 修复前端构建基线

任务：解决当前缺失 `tsconfig.vitest.json` 导致的构建失败，检查 tsconfig 引用关系。

验收：`npm run build`、`npm run type-check`、现有单元测试都通过；不是通过删除测试配置来绕过。

## T0.4 本地基础设施

任务：提供 MySQL 8、Redis 的本地启动方案，推荐 Docker Compose；敏感值从环境变量读取。

验收：空数据库启动后 Flyway 自动建表；重复启动不重复建表；Redis 可连接；README 有停止和清理说明。

## T0.5 测试配置隔离

任务：建立独立测试配置，测试不得依赖开发者本机已有 `fitness` 数据库。

验收：测试可重复运行；数据相互隔离；说明选择 Testcontainers 或测试数据库的原因。

## T0.6 CI 基线

任务：配置一次提交触发的后端测试、前端检查和构建。

验收：成功和故意失败各能被 CI 正确识别；缓存不掩盖失败；日志不泄漏 Secret。

M0 阶段验收：从干净 checkout 按 README 可完成安装、测试和构建。

# M1 公共后端基础

## T1.1 清理重复公共类型

任务：检查两个 `Result`、两个 `MealType` 及移动后的旧包，确定唯一位置并修正引用。

验收：不存在同语义重复类型；编译和测试通过；迁移理由写入变更记录。

## T1.2 统一响应模型

任务：实现成功和失败响应结构、traceId、字符串业务错误码。

验收：Controller 不手工拼不同格式；错误示例与接口文档一致；HTTP 状态和业务 code 各司其职。

## T1.3 领域异常体系

任务：区分 Validation、NotFound、Forbidden、Conflict、Expired、ExternalService 异常，并由全局处理器映射。

验收：不再用 `ResponseStatusException` 承载全部业务语义；未知异常不向客户端泄漏堆栈；异常映射有测试。

## T1.4 审计时间

任务：统一 `createdAt/updatedAt` 自动维护和 UTC 策略。

验收：创建/更新测试验证时间；Entity 不需要每个 Service 重复赋值；数据库与 JVM 时区行为有说明。

## T1.5 CurrentUser 抽象

任务：封装认证上下文读取，Service 使用 currentUserId/currentUserTimezone，而不是信任请求 userId。

验收：无认证、正常用户、管理员角色测试；业务 Service 可在测试中替换当前用户来源。

## T1.6 分页与 ID/时间序列化约定

任务：实现统一 PageResponse，并配置日期、BigDecimal、Enum 序列化。

验收：分页边界、非法排序、ISO-8601 和两位小数响应测试。

M1 阶段验收：新模块可以复用统一异常、用户、时间和返回约定。

# M2 认证与用户

## T2.1 注册 Service 完整验收

检查并补齐 Email 规范化、密码确认、BCrypt、IANA 时区、默认角色/状态和并发唯一冲突。

验收：正常、重复 Email、大小写 Email、密码不一致、无效时区、并发冲突测试。

## T2.2 登录 Service 完整验收

检查密码匹配、禁用状态、统一错误提示和 JWT 签发。

验收：不存在用户和错误密码不泄漏差异；禁用用户 403；日志无密码/JWT。

## T2.3 JWT Provider

任务：实现签发、解析、签名校验、过期校验和 Secret 配置保护。

验收：正确、篡改、过期、错误签名、缺失 claim 测试；生产 profile 无默认弱 Secret。

## T2.4 JWT Filter 与 Security 配置

任务：配置无状态鉴权、公共路径、认证入口和角色保护。

验收：公共接口匿名可用；保护接口 401；ADMIN 接口普通用户 403；无 Session 依赖。

## T2.5 当前用户资料

任务：实现 GET/PATCH `/users/me`，支持昵称和时区。

验收：用户只能改自己；无效时区失败；时区修改不改变已有 FoodRecord 的 recordDate。

## T2.6 认证集成测试

任务：从注册到登录再访问保护接口完成一次真实 HTTP 测试。

验收：数据库保存哈希；Token 可用；跨用户隔离场景作为后续测试基类。

M2 阶段验收：身份可信，后续业务不接受任意 userId。

# M3 Food 与 Nutrition Goal

## T3.1 核对 V1 Migration 与 Entity

任务：逐字段比对 SQL、Entity、索引、可空性、Enum 和外键。

验收：`ddl-auto=validate` 成功；重复 MealType 已处理；每处差异有迁移而不是手改已执行生产脚本。

## T3.2 FoodCategory 查询与管理

任务：实现用户分类列表和 ADMIN 增改/状态接口。

验收：排序、状态过滤、重名冲突、角色测试。

## T3.3 Food 可见性查询

任务：实现公共 Food + 当前用户自定义 Food 搜索和详情。

验收：其他用户私有 Food 在列表和详情都不可见；INACTIVE 不出现在普通搜索；分页和模糊查询测试。

## T3.4 公共 Food 管理

任务：实现 ADMIN 创建、修改、停用，不提供破坏历史的物理删除。

验收：营养正数/非负规则；普通用户 403；修改 Food 不修改已有 FoodRecord 的预备集成测试。

## T3.5 自定义 Food

任务：实现用户创建和修改私有 Food。

验收：owner 和类型由服务端设置；跨用户更新失败；公共发布字段不可伪造。

## T3.6 Goal 日期查询

任务：按任意日期查询有效 Goal。

验收：起始日、结束日、空档日、无目标、跨用户测试。

## T3.7 Goal 切换事务

任务：建立新目标时关闭旧目标，支持部分指标和进入无目标状态。

验收：四项全空失败、0 失败、日期重叠处理、并发唯一冲突、事务回滚测试。

## T3.8 Food 与 Goal OpenAPI

任务：补齐请求、响应、错误码和示例。

验收：实际响应与文档一致；Entity 不直接作为 API 响应。

M3 阶段验收：可维护食品和按日期得到准确可选目标。

# M4 Food Record

## T4.1 营养计算器

任务：建立无数据库依赖的 BigDecimal 计算组件。

验收：100g、非整数重量、0.01g、舍入边界、大值测试；禁止 double；统一 HALF_UP 两位小数。

## T4.2 创建记录 Service

任务：完成 current user、Food 可见性/状态、重量、时间、recordDate、快照、实际值和保存。

验收：客户端不能控制营养值；无 Goal 正常；不同时区跨午夜测试；停用/私有 Food 测试。

## T4.3 单条幂等

任务：以 user + operation + Idempotency-Key 保证创建一次。

验收：重复顺序请求、并发请求、同 key 不同 body 冲突测试；数据库唯一约束存在。

## T4.4 Food Record 详情和历史列表

任务：实现详情、日期/Meal 分页查询和 DTO。

验收：按 occurredAt 排序；无记录空集合；跨用户 ID 返回 404；无 Lazy 序列化问题。

## T4.5 编辑窗口策略

任务：抽取统一 30 天策略并实现服务端校验。

验收：今天、边界第 30 天、第 31 天、用户时区边界测试。

## T4.6 编辑记录

任务：处理只改重量、改时间、改 Food、改 Meal/Note 和乐观锁。

验收：改重量用旧快照；改 Food 换新快照；跨日期重算 recordDate；过期/跨用户/版本冲突测试。

## T4.7 删除记录

任务：实现本人、窗口内删除和审计。

验收：删除后查询和汇总不再出现；跨用户和过期失败；重复删除行为明确。

## T4.8 批量记录

任务：整批校验、单事务保存、批量幂等。

验收：任一行失败零写入；重复批次零新增；每行快照正确；合理限制批量大小。

## T4.9 复制记录

任务：复制上一条/指定记录到新时间，使用当前 Food 标准并生成新事实。

验收：新 ID、新 requestId、新 occurredAt；原记录不变；Food 标准变化可在预览/结果体现。

M4 阶段验收：Food 修改不影响历史、营养计算确定、重复请求不重复写。

# M6 快速记录与食品搜索

# 3. 当前应执行的第一个任务

## 当前任务：T0.1 保护现有工作并建立提交基线

### 为什么从这里开始

当前工作区存在多处已修改、删除和新增文件，包括原型目录移动、后端包结构调整、实体变化和安全代码。如果直接继续开发，后续无法判断某个问题来自旧改动还是新任务，也容易误覆盖已有成果。

### 你需要完成

1. 运行并阅读 `git status`；
2. 逐组判断这些变化分别属于：原型目录重命名、V1 数据模型修订、认证/JWT、公共基础设施或无关临时文件；
3. 检查代码中是否存在真实密码、Secret、本地仓库、构建产物；
4. 更新 `.gitignore`（如确实需要）；
5. 将变化拆成你能解释的语义提交；
6. 保持最终工作区干净，或只留下明确说明的进行中任务。

### 本任务不要做

- 不新增业务接口；
- 不顺手重构所有包；
- 不删除看不懂的文件；
- 不使用强制 reset 覆盖现有工作；
- 不把本地数据库密码或 JWT Secret 提交。

