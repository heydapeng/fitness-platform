# Fitness Platform 业务逻辑设计

> 版本：1.0  
> 状态：开发基线  
> 适用范围：V1 - V4；Future 仅说明边界  
> 依据：第二版 PRD、需求清单、当前数据库与实体实现、简历中的 Fitness Agent 项目承诺

## 1. 文档目标

本文档统一项目中最容易出现分歧的业务语义。开发任何 Controller、Service、Tool、定时任务或前端页面之前，都应先确认实现没有破坏这里定义的不变量。

系统的核心不是聊天，而是可靠保存两类事实：

- 用户实际吃过什么；
- 用户实际完成了什么训练。

Goal、Plan、Meal、标签和 AI 对话都只是比较、组织或操作事实的辅助层。

## 2. 产品定位与主业务闭环

Fitness Platform 面向普通健身记录者，提供传统页面和 AI Assistant 两种入口。两种入口必须调用同一套业务 Service。

### 2.1 饮食闭环

```text
注册/登录
→ 搜索并选择真实 Food
→ 输入重量和实际发生时间
→ 服务端计算营养值
→ 保存 Food 当前标准快照和实际摄入值
→ 按用户时区进入某个 business_date
→ Dashboard/History/Analytics/Export 使用同一查询口径
```

### 2.2 AI 饮食闭环

```text
自然语言
→ Intent + Structured Output
→ Food/单位/日期实体解析
→ Java Service 校验和计算 Preview
→ 保存 Pending Action
→ 用户确认
→ 使用 requestId 调用正式 Service
→ 返回执行结果和最新汇总
```

### 2.3 训练闭环

```text
Exercise Definition
→ 可选 Routine/Training Plan/Schedule
→ Free Workout 或从计划开始
→ 记录 Actual Session/Exercise/Set
→ Finish Session
→ Calendar/History/Analytics/Export
```

## 3. 角色与权限

### 3.1 普通用户 USER

- 管理自己的资料、时区、目标、记录、收藏、自定义食品和自定义动作；
- 查询公共 Food/Exercise/Knowledge；
- 只能访问自己的私有业务数据；
- 不能通过请求参数指定其他用户的数据归属。

### 3.2 管理员 ADMIN

- 维护公共 Food、分类、Exercise 和 Knowledge Document；
- 审核、发布、过期知识文档；
- 管理员身份不自动授予读取用户饮食、训练和对话隐私的权限；
- 管理接口必须显式校验 ADMIN 角色。

### 3.3 AI Assistant

- 不是独立用户，也不是数据所有者；
- 只能代表当前认证用户调用白名单 Domain Tool；
- 不接收或决定 userId；
- 不能直接访问 Repository、EntityManager 或 SQL；
- 所有写操作必须经过 Draft、Preview、Confirm。

## 4. 领域划分

| 领域 | 权威数据 | 主要职责 |
| --- | --- | --- |
| Identity | User、Role、JWT | 身份、状态、当前用户、时区 |
| Nutrition | Goal、Food、FoodRecord | 目标、食品、营养事实和计算 |
| Query | QuerySpec、Summary | Dashboard、History、Analytics 统一口径 |
| Media | Photo/Attachment | 私有附件、上传与记录关联 |
| Export | ExportJob、ExportFile | 异步生成和授权下载 |
| Agent | Conversation、Message、PendingAction、Trace | 编排、确认、短期上下文、审计 |
| Knowledge | Document、Chunk、IndexVersion | 审核知识、检索、引用和版本 |
| Training | Exercise、Routine、Plan、Schedule、Session、Set | 训练计划、执行事实和日历投影 |

领域之间通过 Service DTO 交互，不把 JPA Entity 当作公共接口对象。

## 5. 全局业务不变量

1. 用户事实必须绑定服务端认证上下文中的用户。
2. AI 不可绕过 Service 直接写数据库。
3. Food Record 创建时必须保存完整营养快照。
4. 修改 Food 当前标准不得重算历史 Food Record。
5. Nutrition Goal 完全可选，未设置字段使用 `null`，不能用 `0` 表示未设置。
6. Plan 是未来安排，Session/Set 是实际事实；修改计划不得修改历史事实。
7. 所有 AI 写操作必须确认后执行。
8. 歧义必须显式暴露，不允许 LLM 为了填满 JSON 而猜测。
9. Dashboard、Analytics、Export、AI Query 必须复用同一查询语义和计算服务。
10. Redis、向量库和 Conversation Memory 都不是用户业务事实的权威来源。
11. 新增写操作必须具有服务端幂等能力，不能仅依赖前端按钮防抖。
12. AI、RAG、Redis 或 SSE 故障不能阻塞传统饮食和训练页面。

## 6. 时间与时区

### 6.1 时间字段语义

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `occurredAt` | 饮食真实发生时间 | 饮食时间线和补录 |
| `businessDate` / `recordDate` | 发生时按用户时区得到的业务日期 | 每日统计、Goal 匹配 |
| `startedAt` / `endedAt` | 训练实际开始/结束时间 | 训练事实和时长 |
| `scheduledDate` | 计划投影日期 | Calendar 和完成率 |
| `createdAt` | 系统收到数据的时间 | 审计，不代替发生时间 |
| `updatedAt` | 最后修改时间 | 并发控制和审计 |

### 6.2 规则

- 持久化的时间点统一按 UTC 保存，API 使用带时区偏移的 ISO-8601；
- `businessDate` 在创建事实时根据用户当时的 IANA 时区计算并固化；
- 用户以后修改时区，不静默移动已有事实的业务日期；
- “今天”的边界由当前用户时区决定；
- 历史编辑窗口统一采用固定 30 天：`businessDate >= userToday - 29 days`；
- 超过窗口返回只读错误，不依赖前端隐藏按钮；
- 未来不能创建“已完成”的训练事实；未来 Goal、Plan 和 Schedule 可以创建。

## 7. 身份与账户

### 7.1 注册

1. 规范化 Email：去首尾空格并转小写；
2. 校验 Email 格式、密码长度和确认密码；
3. 校验 Email 唯一；
4. 校验 IANA 时区，未提供时使用 UTC；
5. BCrypt 保存密码哈希，不保存明文；
6. 默认角色 USER、状态 ACTIVE；
7. 数据库唯一约束作为并发注册的最终保护。

### 7.2 登录

1. 使用规范化 Email 查用户；
2. 对“不存在”和“密码错误”返回同一提示，避免账号枚举；
3. 禁用用户不能登录；
4. 成功后签发短期 Access Token；
5. JWT 至少包含稳定用户标识、角色、签发和过期时间；
6. 日志不得输出密码、哈希、JWT 和 Secret。

### 7.3 用户资料与时区修改

- 只允许修改自己的昵称和时区；
- 新时区只影响之后的“今天”判断及新事实；
- 已保存 `recordDate` 不回写。

## 8. Nutrition Goal

### 8.1 语义

Goal 是日期有效的比较基准，不是记录饮食的前置条件。Calories、Protein、Carbs、Fat 可以部分设置。

### 8.2 校验

- 四项不能全部为 `null`；
- 已填写值必须大于 0；
- 精度统一保留两位小数；
- `effectiveDate` 必填；
- `endDate` 可空，但存在时不得早于 `effectiveDate`；
- 同一用户任意业务日期最多命中一条有效 Goal。

### 8.3 创建新目标

在日期 D 创建新目标时：

1. 查询 D 当天已存在的目标；存在则按产品选择“更新同日起点目标”而不是插入重复记录；
2. 找到 D 之前仍开放的上一目标，将其 `endDate` 调整为 D-1；
3. 创建 D 起生效的新目标；
4. 不修改更早日期的 Food Record；
5. 如果需要进入“无目标状态”，结束当前目标而不是创建四项为 0 的目标。

整个过程必须在同一事务内完成，并依赖唯一约束兜底。

### 8.4 日期命中规则

目标 G 对日期 D 有效，当且仅当：

```text
G.effectiveDate <= D
AND (G.endDate IS NULL OR G.endDate >= D)
```

## 9. Food 食品库

### 9.1 类型与可见性

| 类型 | ownerUser | 可见范围 | 谁可修改 |
| --- | --- | --- | --- |
| SYSTEM | null | 全体用户 | ADMIN |
| EXTERNAL | null | 全体用户 | 系统同步/ADMIN |
| USER | 当前用户 | 创建者 | 创建者 |

普通用户可见 `status=ACTIVE` 的公共食品以及自己的 ACTIVE 自定义食品。查询详情也必须重复做可见性校验，不能只保护列表。

### 9.2 搜索

搜索顺序：

```text
规范化 query
→ 可选 Redis 热点结果
→ MySQL 本地模糊搜索
→ 本地候选是否足够
→ 不足时调用第三方
→ Normalize + Validate + Deduplicate
→ 返回候选
→ 用户真正选用时沉淀本地
```

排序建议：完全名称匹配、最近吃过、收藏、热门、模糊相关度。排序只影响展示，不改变营养事实。

### 9.3 第三方标准化与去重

- 外部字段必须映射为内部每 100g 标准；
- 缺少核心宏量营养字段时标记不完整，不可直接记录；
- 首选唯一键为 `provider + externalId`；
- 无稳定 ID 时可使用规范化名称、品牌和营养签名辅助去重；
- 同一外部食品并发落库依赖数据库唯一约束；
- 必须保留来源和许可要求的展示信息。

### 9.4 状态保护

- INACTIVE Food 不能创建新记录；
- 历史记录仍展示快照；
- 被引用 Food 不物理删除；
- Food 修改后主动失效详情和搜索缓存。

## 10. Food Record

### 10.1 创建输入

必填：`foodId`、`amountG`、`occurredAt`、`requestId`。  
可选：`mealType`、`note`、图片关联信息。

服务端忽略客户端提交的实际营养值。客户端预览只用于体验，正式值必须重新计算。

### 10.2 创建流程

1. 从认证上下文获取 userId；
2. 以 `(userId, requestId)` 查询幂等记录；存在则返回第一次结果；
3. 查询 Food，并校验状态和用户可见性；
4. 校验 `amountG > 0` 且不超过系统合理上限；
5. 校验 `occurredAt`，并根据用户时区计算 `recordDate`；
6. 复制 Food 名称和每 100g 宏量营养快照；
7. 计算实际营养；
8. 保存 FoodRecord；
9. 提交事务后清理受影响日期的 Dashboard/Analytics 缓存；
10. 返回记录详情，而不是返回 Entity。

### 10.3 营养计算

对每个指标：

```text
actual = per100g × amountG ÷ 100
```

- 全过程使用 BigDecimal；
- 中间计算使用足够精度；
- API 输出统一保留两位小数；
- 舍入规则统一采用 `HALF_UP`；
- 不使用 `double` 或前端结果作为最终事实。

例：鸡胸每 100g 蛋白质 23.10g，食用 180g：`23.10 × 180 ÷ 100 = 41.58g`。

### 10.4 历史快照

必须固化：Food 名称、Calories/P/C/F 每 100g 标准、amount、实际 Calories/P/C/F。`foodId` 表示来源引用，快照表示历史事实。

### 10.5 编辑

- 先按 `recordId + currentUserId` 查询；查不到统一返回 404；
- 校验 30 天窗口；
- 修改 amount：使用原快照重新计算；
- 修改时间：重新计算业务日期；
- 修改 Food：重新读取新 Food 当前标准并替换整组快照；
- 修改 Meal/Note：不改变营养；
- 使用版本号或 `updatedAt` 做乐观并发控制；
- 编辑后刷新原日期和新日期的统计缓存。

### 10.6 删除

- 只允许本人且在编辑窗口内删除；
- V1 可物理删除，但审计需要记录操作者和记录 ID；
- 删除后 Dashboard、History、Analytics 和 Export 都不再计入；
- 重复删除可返回资源不存在，不应影响其他记录。

## 11. Dashboard、History 与 Analytics

### 11.1 每日汇总

按 `userId + recordDate` 聚合 FoodRecord 的实际 Calories/P/C/F，并匹配该日有效 Goal。

每个指标单独返回：

- `actual`；
- `target`，未设置为 null；
- `remaining = max(target - actual, 0)`；
- `over = max(actual - target, 0)`；
- `completionPercent = actual / target × 100`；
- target 为 null 时 remaining/over/completion 都为 null。

### 11.2 历史

- 指定日期查询返回当日汇总和按 `occurredAt` 升序的记录；
- Meal 只是可选分组，未设置归入 `UNASSIGNED`；
- 无数据返回合法空集合与零 actual，不返回 404。

### 11.3 QuerySpec

统一查询对象至少包含：

```text
domain, dateRange, filters, groupBy, metrics, sort, columns, timezone
```

日期范围、过滤、分组、指标都必须白名单校验。前端图表、表格、导出和 AI 使用相同 QuerySpec，不允许分别实现统计公式。

## 12. 快速记录

### 12.1 最近、常吃、收藏

- 最近吃过：按最近 FoodRecord 去重，附上次重量、时间、Meal；
- 常吃：按滚动 30 天使用次数统计，同频按最近时间；
- 收藏：`userId + foodId` 唯一；Food 停用后保留收藏关系但禁止记录；
- 点击快捷项只生成预填草稿，确认后才创建新事实。

### 12.2 批量记录

- 每行独立选择 Food 和重量；
- 服务端先校验全部行，再一次性保存；
- 任一行失败则整批不写入；
- `batchRequestId` 对整批幂等，各行可派生稳定子 requestId；
- 每个 Food 最终仍是独立 FoodRecord。

### 12.3 复制

复制上一条、上一餐或昨天记录，本质是创建新事实：

- 复制 Food 和 amount；
- 目标发生时间必须重新指定；
- Meal 可明确继承并允许修改；
- 使用 Food 当前标准还是历史快照必须明确。本项目选择重新选择当前 Food 标准，使新事实与当前食品库一致，并在预览中展示变化。

## 13. 图片与附件

- 图片默认私有；
- 支持关联单条记录或同批/同餐记录组；
- 结构化记录先成功，图片上传失败不能回滚记录；
- 文件类型、大小、数量和内容类型由服务端校验；
- 对象存储只保存二进制，数据库保存 owner、objectKey、hash、状态和关联关系；
- 下载使用短期授权地址或受保护的流式接口；
- 删除记录时按照附件引用关系决定删除关联，而不是盲删共享图片。

## 14. Export

### 14.1 两种入口

- Export Current Result：直接保存当前 QuerySpec；
- My Data Export：用户重新选择范围、数据域、明细/汇总和是否包含图片。

### 14.2 状态机

```text
PENDING → PROCESSING → SUCCEEDED → EXPIRED
                    └→ FAILED
```

- 任务属于当前用户；
- Worker 必须再次应用用户数据范围；
- 无数据时不生成误导性空包；
- 下载链接过期不删除源业务数据；
- 重试生成新 Job 或按明确规则重试旧 Job；
- CSV/XLSX/ZIP 内容必须可以追溯原 QuerySpec。

## 15. Agent Core

### 15.1 意图

至少区分查询、搜索、记录和未知：

`QUERY_TODAY_NUTRITION`、`QUERY_NUTRITION_RANGE`、`SEARCH_FOOD`、`RECORD_FOOD`、`QUERY_FOOD_HISTORY`、`QUERY_NUTRITION_GOAL`、`QUERY_ANALYTICS`、`UNKNOWN`。

### 15.2 Structured Output

结构化结果必须包含：意图、解析参数、缺失字段、歧义、未解析实体和不支持单位。Schema 必须允许不完整结果，严禁用模型猜测补齐关键参数。

### 15.3 Tool 设计

- Tool 是 Application Service 的薄适配层；
- 输入输出使用专用 Tool DTO；
- Tool 不暴露 JPA Entity；
- Tool 不接收 userId；
- 读 Tool 可以直接执行；
- 写 Tool 分成 `prepare` 和 `execute`，prepare 不写正式事实。

### 15.4 Food Resolve

每个自然语言 Food 都必须映射真实 foodId：

- 唯一高置信候选：选入草稿，但仍需整单确认；
- 多候选：保存候选并等待用户选择；
- 无候选：进入第三方搜索或提示创建自定义食品；
- 模型不得从互联网编造营养值。

### 15.5 Pending Action 状态机

```text
PARSED
→ RESOLVING
→ READY_FOR_CONFIRMATION
→ CONFIRMED
→ EXECUTING
→ SUCCEEDED | FAILED

任意确认前状态 → CANCELLED
等待过久 → EXPIRED
```

Pending Action 至少保存 actionId、userId、intent、服务端解析后的参数、Preview 快照、版本、requestId、状态和 expiresAt。

确认时只提交 `actionId + previewVersion`，服务端读取可信 Pending Action；不得信任前端重新提交的一整份业务参数。

### 15.6 幂等和并发

- 同一 action 只能从 READY 原子迁移一次；
- requestId 在最终业务 Service 仍需唯一约束；
- 重复 Confirm 返回第一次结果或 EXECUTING 状态；
- SSE 断线不会回滚已提交事务，也不会让重连重复执行；
- Preview 被编辑后版本加一，旧版本 Confirm 返回冲突。

### 15.7 Conversation Memory

Redis 可保存对话摘要、最近实体引用、最近日期范围、Pending Action 和 Tool 结果摘要。今天实际摄入、当前 Goal、Food 状态等实时事实每次都重新查询 MySQL。

### 15.8 SSE

允许展示业务阶段：`UNDERSTANDING`、`SEARCHING_FOOD`、`QUERYING_DATA`、`WAITING_CONFIRMATION`、`EXECUTING`、`ANSWERING`、`DONE`、`ERROR`。不得输出模型内部 Chain-of-Thought。

### 15.9 Trace

一次调用链关联 conversationId、messageId、agentRunId、actionId、toolCallId、requestId。记录结构化输入摘要、Tool 名称、耗时、状态和错误类型，但脱敏 Password、JWT、Secret 和不必要的完整 Prompt。

## 16. RAG

### 16.1 知识与事实分离

- 用户记录和目标来自 MySQL Tool；
- 公共知识来自 APPROVED 且有效的知识文档；
- Memory 只帮助理解指代；
- 模型常识不能覆盖 Tool 事实或伪装成引用来源。

### 16.2 文档生命周期

```text
DRAFT → REVIEWING → APPROVED
                  └→ REJECTED
APPROVED → EXPIRED
```

只有 APPROVED 且未过期版本进入正式检索。新版本发布不物理删除旧版本，Trace 记录使用的版本。

### 16.3 索引链路

```text
Document
→ Normalize
→ Semantic Chunk
→ Metadata
→ Embedding
→ Versioned Vector Index
```

Chunk 保留 documentId、version、heading、topic、source 和序号。Embedding 模型或切分策略变化时创建新索引版本并支持重建。

### 16.4 查询链路

```text
Original Query
→ Query Rewrite
→ Metadata Filter + TopK Retrieval
→ Relevance Threshold
→ Rerank
→ Select Context
→ Answer + Actual Sources
```

没有达到阈值的可靠内容时明确说明知识库依据不足，不拼凑无关 Chunk。

### 16.5 Tool + RAG 回答

事实优先级：当前 Tool 事实 > 用户本轮输入 > APPROVED RAG > Memory > 模型常识。回答需要区分“你的数据”和“一般知识”，不能自动改变 Goal 或 Plan。

## 17. Training

### 17.1 核心对象

- Exercise：可被记录引用的动作定义；
- Routine：不绑定日期的可复用训练模板；
- TrainingPlan：未来安排；
- PlanVersion：计划的不可变版本；
- ScheduledWorkout：某日期的计划投影/快照；
- WorkoutSession：一次实际训练；
- SessionExercise：Session 中有顺序的动作；
- WorkoutSet：实际完成的组事实。

### 17.2 自由训练

用户不需要 Plan：开始 Session、添加动作和 Sets、结束后形成正式事实。系统同一时间默认只允许一个进行中的 Session；再次开始时提示继续或结束。

### 17.3 Plan 与 Schedule

- 支持 WEEKLY、REPEATING_CYCLE 和 DATE_SPECIFIC；
- N 天循环允许 Workout Day 和 Rest Day；
- 多个 ACTIVE Plan 可同时投影到同一天；
- 冲突只提示，不自动删除或重排；
- Missed Schedule 保持未完成，不自动顺延；
- Plan 修改创建新版本，未来投影使用新版本，历史保留旧快照。

循环日期计算示意：

```text
cycleDay = ((targetDate - startDate) mod cycleLength) + 1
```

开始日期为空的循环计划不能投影到 Calendar，启用时必须补齐可计算锚点。

### 17.4 从计划开始训练

Schedule 目标复制到 Session Draft；用户录入实际 Set；结束时即使未完成目标也允许保存。Session 可关联 sourceScheduleId，但实际数据不回写覆盖计划目标。

### 17.5 Set 校验

- weight、reps、duration、distance、RPE、RIR 按动作类型选择性填写；
- 未使用字段保持 null；
- RPE 范围 1-10，RIR 不得为负；
- completed=false 的计划占位不计入完成统计；
- 不将跑步、自重、辅助重量强行合并进外部负重 Volume。

### 17.6 训练历史

- 30 天内可补录、编辑、删除；
- 未来 completed Session 被阻止；
- 合法修改后 PR、Volume、完成率重新计算或失效缓存；
- 停用 Exercise 不破坏历史名称/目标快照。

## 18. Training Analytics

- Frequency：按日期范围统计 Session；
- Completed Sets/Reps：只统计完成事实；
- Load Volume：仅 `weight × reps` 适用动作；
- Weight PR：历史成功 Set 的最高外部重量；
- Estimated 1RM：只对适用动作计算并标明估算及公式版本；
- Plan Completion：`Completed Scheduled Workouts / Planned Scheduled Workouts`；
- Free Workout 默认不计某 Plan 完成率，除非用户明确关联 Schedule；
- 所有统计可追溯到 Session/Set，并与图表、表格、导出、AI 共用 Training QuerySpec。

## 19. AI Training

- 自然语言训练记录先解析 Exercise 和 Set，再生成 Preview；
- Exercise 多候选必须选择；
- 关联当天 Schedule 必须询问用户；
- AI Plan 只生成结构化草稿，可进入传统编辑器；
- Confirm 后调用正式 Training Service 创建 Plan/Session；
- 修改计划生成 before/after Change Draft，并基于当前版本做并发校验；
- AI 不因表现自行调整重量、移动 Missed Schedule 或修改 Plan；
- 训练事实来自 Tool，一般建议来自 RAG。

## 20. 缓存、事务与一致性

### 20.1 权威来源

MySQL 是用户业务事实的权威来源；Redis 只用于缓存、锁、Memory、Pending Action 和短期状态；向量库只用于知识召回；对象存储只保存附件和导出文件。

### 20.2 事务边界

- 单条记录创建：快照、计算值和记录同事务；
- 批量记录：整批校验、整批提交；
- Goal 切换：关闭旧目标和创建新目标同事务；
- Confirm：状态原子迁移和业务写入需要可恢复设计；
- 缓存清理在事务提交后执行，失败时允许 TTL 最终恢复。

### 20.3 缓存原则

- Key 必须包含数据域和必要的用户隔离维度；
- 不缓存 JWT、密码或完整敏感 Prompt；
- 写成功后主动失效相关缓存；
- 缓存未命中回源数据库；
- 热点重建可以使用短锁，但锁失败不能返回错误事实。

## 21. 异常、降级与审计

- 参数错误返回稳定业务错误码和字段信息；
- 不把堆栈、SQL、Secret 暴露给客户端；
- 第三方 Food API 故障时仍返回本地结果；
- 图片失败不回滚饮食记录；
- Export 失败不影响源数据；
- LLM 故障时传统页面可用；
- RAG 故障时 Personal Data Tool 可用；
- 所有关键写操作记录操作者、资源、requestId、结果和时间；
- 管理员维护公共数据与知识状态必须留审计信息。

## 22. 核心端到端场景

### 22.1 无 Goal 记录午餐

用户选择鸡胸 200g，发生时间 12:30，不选 Meal。系统保存快照和实际营养；Dashboard 返回实际值，所有 target 相关字段为 null。

### 22.2 Food 被修改

9 月 1 日记录使用旧快照；9 月 15 日管理员修改 Food；9 月 1 日结果不变，之后的新记录使用新标准。

### 22.3 AI 重复确认

第一次 Confirm 已写入但 SSE 断线；第二次使用相同 actionId/requestId，服务端返回第一次结果，不创建重复记录。

### 22.4 Tool + RAG

“我今天还差多少蛋白质，晚上怎么补？”先通过 Tool 取得 actual/target/difference，再检索 APPROVED 蛋白质知识，回答明确区分个人数据和一般建议并附真实来源。

### 22.5 九天训练循环

系统按 startDate 和 cycleLength 投影 Day1-Day9；休息日显示为计划信息；某日未练不移动后续 Day；修改计划只影响新版本生效后的未来投影。

## 23. 明确不做

核心主线不包含：AI 图片估算营养、自动医疗诊断、AI 自主修改目标/计划、复杂社区 Feed、私信群聊、排行榜、教练商业体系、Apple Health/Garmin 接入、任意历史文件智能导入。它们只能在核心闭环稳定后单独立项。
