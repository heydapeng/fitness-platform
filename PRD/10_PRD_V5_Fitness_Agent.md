# Fitness Nutrition Platform — PRD V5：统一首页 Fitness Agent

## 一、版本概述

V5 将 V4 的“首页 AI + 只读 Tool”和 V4.5 的“RAG 知识增强”升级为真正可执行系统业务的 Fitness Agent。

最终产品形态是：

> 用户打开首页，就能直接通过文字、语音或文件告诉 AI 自己想做什么。AI 理解意图后调用系统已有业务能力完成查询、记录、计划制定、修改、数据导入和数据导出。

用户不必先理解系统菜单结构。

例如：

- “中午吃了 300g 米饭、200g 鸡胸和两个鸡蛋，帮我记一下。”
- “刚称了 72.4kg，体脂 18.2%。”
- “今天卧推 80kg 做了 8、8、7 三组，帮我记训练。”
- “给我做一个每周四练的增肌计划，我周三和周五没空。”
- “把周一腿训练换到周二，深蹲改成哈克深蹲。”
- “这是我以前记饮食的 Excel 和几张截图，帮我导入。”
- “把最近三个月体重、围度、每日摄入和饮食照片导出来。”

AI 不直接操作数据库。它负责理解、结构化和编排；最终所有业务结果必须通过系统已经存在的 Service/API/Tool 完成。

## 二、版本目标

1. 首页 AI 成为查询和业务操作的统一入口；
2. 支持文字和语音转文字；
3. 支持在对话中上传图片、表格、文档和其他历史记录文件；
4. 使用 Structured Output 将自然语言转成受约束业务意图；
5. 支持自然语言记录饮食、身体数据和训练数据；
6. 支持 AI 创建、调整和解释训练计划；
7. 支持 AI 解析外部历史数据并映射到系统标准模型；
8. 支持 AI 触发用户数据导出；
9. 对批量、高影响和不确定写操作提供预览与确认；
10. 对简单、低风险、无歧义操作减少不必要的确认步骤；
11. 写操作具备幂等、防重复、权限隔离和调用链路追踪；
12. Tool 业务数据与 RAG 知识可以在同一次回答中组合使用；
13. AI 服务故障时，传统业务页面仍能完整使用。

## 三、V5 Agent 能力地图

### 1. 查询类

- 查询今日/历史饮食；
- 查询每日营养；
- 查询营养目标；
- 查询食品；
- 查询身体趋势；
- 查询训练计划；
- 查询训练历史；
- 查询 PR/训练统计；
- 查询导出任务；
- RAG 健身知识问答。

### 2. 记录类

- 新增饮食记录；
- 修改受支持的饮食记录；
- 新增身体测量；
- 新增训练记录；
- 对已有训练补充备注等低风险字段。

### 3. 计划类

- 创建训练计划草稿；
- 修改训练计划；
- 调整训练日；
- 替换动作；
- 修改组数/次数/RPE 等计划目标；
- 启用计划；
- 暂停计划；
- 复制现有计划并调整。

### 4. 数据迁移类

- 上传历史数据文件；
- AI 判断数据类型；
- 解析外部字段；
- 映射到系统模型；
- 检测异常和重复；
- 生成预览；
- 用户确认后批量导入。

### 5. 数据导出类

- 自然语言选择时间范围；
- 自然语言选择数据域；
- 创建导出任务；
- 查询导出状态；
- 返回下载入口。

### 6. 知识与解释类

- 基于 RAG 回答营养/训练知识；
- 将用户实时数据与审核知识结合；
- 解释“为什么这个计划这么安排”；
- 解释某个指标或趋势，但不虚构用户事实。

## 四、首页 AI 统一入口

### 1. 首页结构

Dashboard 顶部或首屏核心区域显示：

```text
今天想记录什么，或者需要我帮你做什么？

[ 输入文字，或直接说……                    ]
[附件] [麦克风]                         [发送]

快捷操作：
[记录一餐] [记录体重] [安排训练] [导出数据]
```

AI 输入框不应被设计成次级入口。

V5 以后，首页同时保留：

- AI 输入区；
- 今日营养摘要；
- 今日训练；
- 身体最新数据；
- 快捷手动记录按钮。

### 2. AI 是入口，不是唯一界面

复杂记录仍可以打开传统表单。

例如用户说：

> “我想自己详细改这个训练计划。”

AI 可以打开对应计划页面，而不是强迫用户继续聊天。

## 五、输入方式

### 1. 文字

支持普通自然语言、多行文字和复制粘贴历史记录。

### 2. 语音转文字

继承 V4：

```text
语音 → 转写文字 → 用户可编辑 → 发送 → Agent
```

V5 特别要求正确处理：

- 数字；
- kg/g/ml；
- 动作名；
- 食品名；
- 日期；
- 组数、次数；
- RPE/RIR。

转写低置信度时，应突出可疑片段让用户检查。

### 3. 图片

用户可在对话中上传：

- 食物照片；
- 身体进度照片；
- 旧记录截图；
- 表格截图；
- 训练笔记截图。

图片可能承担两种角色：

#### 业务附件

例如用户说：

> “午饭就是这些，米饭 300g，鸡胸 200g，帮我记一下。”

上传的照片可直接作为这餐的饮食图片附件保存。

#### 导入来源

例如用户上传旧 App 的饮食截图，要求导入历史记录。

### 4. 文件

支持用户上传常见历史记录文件，例如：

- CSV；
- XLS/XLSX；
- JSON；
- TXT；
- Markdown；
- DOC/DOCX；
- PDF；
- 图片/扫描件；
- 包含多个文件的 ZIP（可逐步支持）。

产品目标是“尽可能自动理解用户现有数据”，而不是承诺每种任意二进制格式都能百分百成功。

无法可靠解析时，系统需要明确告诉用户问题在哪里，并提供人工映射或重新上传方案。

## 六、Agent 意图与 Structured Output

### 1. 产品原则

模型不能直接根据自由文本拼数据库请求。

所有可执行请求先转换为明确的业务意图，再进入校验和 Tool 调用。

### 2. 主要意图类型

至少包括：

- QUERY_NUTRITION；
- RECORD_FOOD；
- UPDATE_FOOD_RECORD；
- RECORD_BODY_MEASUREMENT；
- RECORD_WORKOUT；
- CREATE_TRAINING_PLAN；
- UPDATE_TRAINING_PLAN；
- EXPORT_USER_DATA；
- IMPORT_USER_DATA；
- ADJUST_NUTRITION_GOAL；
- KNOWLEDGE_QUESTION；
- MIXED_QUERY。

PRD 不规定具体枚举命名，但产品必须能区分业务类型。

### 3. Structured Output 需要表达

- 用户想做什么；
- 目标对象；
- 日期/时间范围；
- 结构化参数；
- 缺失字段；
- 歧义项；
- 数据来源；
- 风险等级；
- 是否需要确认。

### 4. 不确定性

AI 必须能够表达“我不确定”，而不是所有字段都强行填值。

## 七、确认策略

V5 不采用“所有操作都确认一次”的笨重方案，而是按风险分级。

### 1. 可直接执行的低风险操作

满足以下条件时，可直接执行并提供“撤销/查看”结果：

- 单条数据；
- 参数完整；
- 无实体歧义；
- 不会覆盖大量历史数据；
- 用户意图明确；
- 操作可轻易修正。

例如：

> “今天体重 72.4kg。”

如果日期和单位明确，可以直接记录，然后回复：

> “已记录今天体重 72.4kg。”

### 2. 必须确认的操作

- 食品候选不唯一；
- 份量无法可靠换算；
- 修改/删除已有事实；
- 改营养目标；
- 创建完整训练计划并准备启用；
- 大规模修改训练计划；
- 批量历史数据导入；
- 覆盖冲突数据；
- 大范围数据导出且包含敏感图片；
- 任何低置信度操作。

### 3. 确认卡片

确认内容必须是用户能理解的业务结果，而不是 Tool JSON。

## 八、自然语言饮食记录

### 1. 标准场景

用户：

> “中午吃了 300g 米饭、200g 鸡胸肉和两个鸡蛋，帮我记一下。”

系统：

```text
识别午餐
→ 提取食品和份量
→ 搜索食品
→ 匹配实体
→ 判断鸡蛋“个”是否可可靠换算
→ 必要时询问/确认
→ 调用饮食记录 Tool
→ 关联本次上传食物图片（如有）
→ 查询最新今日营养
→ 返回完成结果
```

### 2. 食品实体匹配

不允许模型创造不存在的 foodId。

“鸡胸肉”对应多个食品时：

- 候选差异小且系统有默认规则，可展示默认匹配；
- 营养差异明显时让用户选择；
- 用户说“就是刚才那个”可结合 Memory 找最近实体，但仍执行业务校验。

### 3. 图片关联

用户可以：

> “这是我今天午饭的照片，另外吃了 300g 米饭、200g 鸡胸。”

记录完成后，该图片一起保存到饮食记录/餐次中，并在后续导出时可一起导出。

### 4. 语音饮食记录

用户说：

> “早餐两个鸡蛋，一杯牛奶，香蕉一根。”

转写后：

- 用户可先修改文字；
- Agent 检查“杯/根/个”是否存在可靠份量；
- 无法确定时只追问不确定项。

## 九、自然语言身体数据记录

### 1. 基础场景

用户：

> “今天早上 72.4kg，体脂 18.2，腰围 81。”

AI 应识别为同一天的一组身体测量。

### 2. 图片

如果同时上传身体进度照片：

- 作为该日期身体记录附件；
- 用户可选择正面/侧面/背面标签；
- 不强制 AI 对身材外观作评价。

### 3. 重复日期

如果当天已经有身体记录：

- 可新增第二次测量；或
- 提示是否更新当天已有记录；

产品行为需要明确，不能静默覆盖。

## 十、自然语言训练记录

### 1. 使用场景

用户训练结束后说：

> “今天卧推 80kg 做了 8、8、7，飞鸟 15kg 三组每组 12。”

系统应解析：

- 日期；
- 动作；
- 重量；
- 各组次数；
- 组数；
- 训练 Session 归属。

### 2. 动作匹配

动作名存在别名时可以匹配已有动作；多个候选时询问。

### 3. 与当前计划关联

如果今天计划中正好包含卧推/飞鸟，可提示是否记入今天计划训练。

不得因为计划写了 4 组，就把用户实际只完成 3 组自动补成 4 组。

实际记录优先保存真实完成事实。

## 十一、AI 制定训练计划

### 1. 产品定位

AI 计划不是一段聊天文本，而是 V2 训练计划业务能力的自然语言创建入口。

用户说：

> “帮我做一个 8 周增肌计划，每周练 4 天，周三和周五没时间，健身房器械比较全，我想重点练胸背。”

AI 最终必须生成可保存、可编辑、可执行的结构化训练计划。

### 2. 计划前信息收集

AI 根据已有用户资料和对话判断是否缺少：

- 训练目标；
- 每周可训练天数；
- 可训练星期；
- 每次可训练时长；
- 训练经验；
- 可用器械；
- 重点肌群；
- 用户明确的动作偏好/禁用动作；
- 计划周期。

缺少关键约束时，应一次尽量集中询问，不要无止境逐项追问。

### 3. 生成计划草稿

计划草稿展示：

- 计划名称；
- 周期；
- 每周安排；
- 每个训练日目标；
- 动作；
- 组数；
- 次数/次数范围；
- RPE/RIR；
- 休息建议；
- 简要设计说明。

### 4. 用户确认

用户可：

- 保存并启用；
- 保存为草稿；
- 继续让 AI 调整；
- 打开传统计划编辑器手动改；
- 取消。

### 5. 保存规则

确认后：

- AI 调用训练计划创建 Tool；
- 创建真正的 V2 训练计划；
- Dashboard 今日训练能够读取；
- 用户进入传统训练计划页面也能看到并继续编辑。

禁止出现：

> AI 聊天里有一份“计划”，但训练模块里没有。

### 6. 后续自然语言调整

支持：

- “周三没空了，把腿放到周四。”
- “卧推换成哑铃卧推。”
- “周六时间只有 45 分钟，帮我缩短。”
- “这个计划太累，把每个训练日总组数降一点。”

AI 先读取当前计划，再提交结构化修改。

### 7. 计划解释

当用户问：

> “为什么腿只安排一次？”

AI 可以结合：

- 当前计划实际内容；
- 用户设定约束；
- RAG 训练知识；

进行解释，但不应该谎称用户没说过的限制。

## 十二、AI 历史数据导入

### 1. 产品目标

用户可能已经在：

- Excel；
- 备忘录；
- 其他健身 App；
- Word/PDF；
- 截图；
- 手写照片；
- JSON/CSV；

记录了几年健身数据。

平台应尽量降低迁移成本，让 AI 负责理解外部数据格式并映射到系统标准数据。

### 2. 导入入口

支持两种入口：

#### 数据中心

```text
我的数据 → 导入历史数据
```

#### 首页 AI

用户直接说：

> “这是我之前的记录，帮我导入。”

然后上传文件。

### 3. 可导入的数据域

首期重点：

- 饮食记录；
- 每日营养历史（如果只有汇总没有明细，应区分）；
- 身体测量；
- 训练历史；
- 训练计划；
- 身体/饮食图片附件（能可靠对应时）。

### 4. 文件识别

上传后系统先判断：

- 文件格式；
- 是否包含表格；
- 是否扫描件；
- 语言；
- 可能的数据类型；
- 日期格式；
- 单位；
- 多 Sheet/多页结构；
- 是否有多个数据域混合。

### 5. AI 字段映射

示例外部 Excel：

```text
日期 | 早餐 | 卡路里 | P | C | F | 体重
```

AI 可映射：

- 日期 → recordDate；
- 早餐文本 → 饮食候选；
- 卡路里 → calories；
- P/C/F → 宏量营养；
- 体重 → body weight。

但映射不是正式写入。

### 6. 导入预览

正式导入前必须展示：

- 识别到的数据类型；
- 总行数/总记录数；
- 可直接导入数量；
- 有警告数量；
- 无法识别数量；
- 字段映射；
- 日期范围；
- 单位推断；
- 重复数据检测结果。

### 7. 置信度与异常项

每条/每类数据可以标记：

- 高置信度；
- 需要确认；
- 无法导入。

例如：

> “03/04/25”

可能是 2025-03-04，也可能是 2025-04-03，不能直接猜。

### 8. 单位转换

如果外部使用 lb、oz、斤等单位：

- 明确识别单位；
- 预览时展示转换后的系统单位；
- 不确定单位时要求用户选择。

### 9. 食品匹配

历史饮食文本中的“鸡胸”“牛奶”等需要与食品库匹配。

如果没有足够信息：

- 可导入为历史文本记录/待匹配状态（如果产品支持）；或
- 让用户选择映射；
- 不允许 AI 随机对应营养差异很大的食品。

### 10. 重复检测

导入前检查可能重复：

- 同日期；
- 同食品/动作；
- 同重量/组数据；
- 与系统已有记录高度相同。

用户可选择：

- 跳过疑似重复；
- 覆盖/更新（仅允许明确支持的场景）；
- 仍然新增。

### 11. 批量确认

用户确认后，Agent 调用批量业务能力写入。

导入过程中：

- 每条数据仍需满足系统业务校验；
- 不绕过用户隔离；
- 不因 AI 导入而创建非法日期/负数等数据。

### 12. 部分失败

大批量导入中可能有部分记录失败。

结果页展示：

- 成功数量；
- 跳过数量；
- 失败数量；
- 失败原因；
- 可下载错误清单；
- 可重新处理失败项。

### 13. 导入报告

导入结束后生成一份用户可理解的报告：

> 共识别 1,286 条记录，成功导入 1,241 条，跳过 31 条疑似重复，14 条需要你补充信息。

## 十三、AI 数据导出

### 1. 产品定位

V1.2 已存在手动数据导出。V5 AI 只负责把自然语言转换为导出条件并调用同一能力。

### 2. 示例

用户：

> “把我最近三个月身材变化和每天吃了多少导出来，饮食照片也一起要。”

AI 应识别：

- 时间范围：最近 3 个月；
- 身体数据；
- 每日营养汇总；
- 饮食明细（可询问是否需要）；
- 饮食图片：包含。

### 3. 导出预览

创建前展示：

- 时间范围；
- 数据类型；
- 图片数量；
- 预计导出内容；
- 是否包含身体照片等敏感媒体。

### 4. 创建任务

用户确认后调用导出 Tool。

AI 不自己手工遍历数据库拼文件。

### 5. 状态反馈

导出处理中：

> “已开始整理你 2026-06-20 至 2026-09-20 的数据。”

完成后：

> “导出完成，包含身体测量、每日营养、饮食明细和 86 张饮食图片。”

并提供下载入口。

## 十四、Tool + RAG 融合

### 1. 用户事实与知识解释

用户：

> “我今天蛋白质还差多少，晚上怎么吃比较合适？”

系统组合：

- Tool：今天实际差额；
- RAG：审核过的蛋白质/饮食知识；
- LLM：组织成答案。

### 2. 训练计划生成

AI 制定计划时可同时使用：

- 用户结构化资料；
- 用户训练历史；
- 当前计划；
- RAG 训练知识；
- 用户本次明确约束。

但最终保存计划的数据必须来自结构化计划草稿。

### 3. 来源优先级

1. 当前业务数据；
2. 用户本轮明确输入；
3. 审核后的 RAG；
4. Conversation Memory；
5. 模型一般知识。

低优先级内容不能覆盖高优先级事实。

## 十五、Conversation Memory

### 1. 需要记住

- 最近话题；
- 最近引用食品；
- 最近动作；
- 当前计划；
- 最近查询结果摘要；
- Pending Action；
- 当前导入/导出任务上下文。

### 2. 示例

```text
用户：帮我记录 200g 熟鸡胸。
AI：已记录。
用户：再加 100g 刚才那个。
```

系统理解“刚才那个”为熟鸡胸。

### 3. 不作为长期事实

Memory 不能代替：

- 今天实际总摄入；
- 当前计划最新版本；
- 最新体重；
- 导入是否真正完成。

这些仍需查询业务系统。

## 十六、写操作安全与幂等

### 1. 当前用户上下文

Agent 不能让模型自行提供 userId 来决定数据归属。

### 2. 业务能力复用

例如饮食 Tool 仍然执行：

- 食品有效性；
- 重量校验；
- 日期校验；
- 营养计算；
- 历史快照；
- 用户隔离。

训练计划 Tool 仍然执行 V2 的计划规则。

导出 Tool 仍然执行 V1.2 的用户数据范围规则。

### 3. requestId 幂等

需要覆盖：

- 用户重复点击；
- SSE 中断重试；
- Tool 超时；
- 模型重复触发同一操作；
- 批量导入任务重复提交。

同一个业务意图不能因为网络问题执行两次。

## 十七、SSE 与执行过程反馈

### 1. 用户可见状态

复杂请求可展示：

- 正在理解；
- 正在读取你的数据；
- 正在匹配食品；
- 正在生成训练计划；
- 正在解析文件；
- 正在检查重复数据；
- 等待你确认；
- 正在保存；
- 正在创建导出；
- 完成。

### 2. 不展示内部推理

只展示业务状态，不显示模型隐式推理过程。

### 3. 写入成功但连接断开

如果业务已经成功写入，SSE 断开：

- 重试不能重复写；
- 系统能恢复并告诉用户刚才操作实际已成功。

## 十八、Agent / Tool Trace

### 1. 产品目标

开发者能够回答：

- AI 理解成了什么意图？
- 提取了什么参数？
- 调用了哪个 Tool？
- Tool 是否成功？
- 是否要求用户确认？
- 导入哪一步失败？
- RAG 检索了什么？
- 最终是否真正写入？

### 2. 需要关联的过程

- 会话；
- Agent Run；
- Structured Output；
- Tool 调用；
- Tool 结果；
- 用户确认；
- RAG 检索；
- 导入任务；
- 导出任务；
- 最终状态。

### 3. 隐私

Trace 不能暴露：

- 密码；
- JWT；
- Secret；
- 不必要的完整敏感文件内容。

## 十九、典型端到端场景

### 场景 A：语音记录午餐

```text
用户点麦克风：
“中午吃了三百克米饭两百克鸡胸还有两个鸡蛋”
→ 转写文字
→ 用户发送
→ Structured Output
→ 食品匹配
→ 鸡蛋份量需要确认
→ 用户确认
→ 调用饮食 Tool
→ 保存记录
→ 返回“已记录，今天蛋白质还差……”
```

### 场景 B：文字记录身体数据

```text
用户：首页输入“今天72.4kg，体脂18.2”
→ 参数明确
→ 低风险直接记录
→ 返回结果卡
→ 支持撤销/查看身体记录
```

### 场景 C：附食物图片记录

```text
用户上传一张午餐照片
并输入“米饭300g，鸡胸200g”
→ AI记录结构化食品
→ 图片作为午餐附件保存
→ 以后历史和导出都能看到图片
```

### 场景 D：AI 制定训练计划

```text
用户：
“我想增肌，每周四练，周三周五没空，每次大概一小时，重点胸背。”
→ 读取已有训练数据和用户资料
→ 补充必要问题（如训练经验/器械）
→ 生成结构化计划草稿
→ 展示每周安排和动作组次
→ 用户说“周六腿太累，换成上肢”
→ AI修改草稿
→ 用户确认启用
→ 调用训练计划 Tool
→ V2计划页面出现正式计划
```

### 场景 E：修改已有训练计划

```text
用户：
“把我计划里周一的杠铃卧推换成哑铃卧推，其他不动。”
→ 查询当前计划
→ 定位周一训练日和动作
→ 展示变更前后
→ 用户确认
→ 调用修改计划 Tool
→ 历史训练不受影响
```

### 场景 F：导入 Excel 历史数据

```text
用户上传 old_fitness.xlsx
并说“这是我去年记录的饮食和体重，帮我导进来。”
→ AI识别两个数据域
→ 识别日期、热量、P/C/F、体重字段
→ 检测单位和日期格式
→ 检测系统已有重复数据
→ 展示导入预览
→ 用户修正一个日期列格式
→ 确认导入
→ 批量业务 Tool 写入
→ 返回导入报告
```

### 场景 G：导入截图

```text
用户上传旧App截图
→ 识别表格/文字
→ 解析日期、食品和营养
→ 低置信度字段标黄
→ 用户修正
→ 确认后导入
```

### 场景 H：导出身体变化 + 饮食图片

```text
用户：
“把最近三个月体重腰围和每天吃多少都导出来，吃饭的照片也带上。”
→ 识别时间范围和数据域
→ 展示将包含的内容和图片数量
→ 用户确认
→ 创建导出任务
→ 完成后返回下载入口
```

### 场景 I：RAG + 用户数据

```text
用户：
“今天蛋白质还差多少？训练后为什么要补蛋白质？”
→ Tool查询差额
→ RAG检索审核知识
→ 返回用户实时数据 + 知识解释 + 来源
```

## 二十、异常与降级

| 场景 | 系统行为 |
| --- | --- |
| 语音转写数字错误 | 用户发送前可修改；低置信度突出提示 |
| Structured Output 缺字段 | 只追问必要字段，不执行写入 |
| 食品候选过多 | 让用户选择 |
| 文件格式未知 | 尝试提取；失败则说明无法解析并建议转换/人工映射 |
| 扫描 PDF 质量差 | 标记低置信度，不批量静默写入 |
| 日期格式歧义 | 要求用户选择日期解释 |
| 批量导入存在重复 | 预览中标记，用户选择处理策略 |
| 导入部分失败 | 返回成功/失败清单，允许处理失败项 |
| 训练计划约束不足 | 集中询问关键限制 |
| AI 生成不存在的动作 | 必须通过动作搜索/匹配后才能保存 |
| Tool 业务校验失败 | 将真实业务原因反馈给用户 |
| RAG 不可用 | 纯业务操作仍可执行，知识部分降级 |
| Memory 不可用 | 明确请求仍可处理，指代要求用户重述 |
| SSE 中断 | 查询请求状态，依赖幂等避免重复 |
| 导出任务较大 | 进入任务状态，不阻塞聊天 |
| 用户取消确认 | 不执行写 Tool |

## 二十一、业务规则与约束

1. 首页 AI 是统一自然语言入口，但传统页面必须继续完整可用。
2. LLM 负责意图理解、参数抽取、Tool 选择和语言组织。
3. Java Service/API/Tool 负责权限、校验、计算、事务和持久化。
4. AI 不直接访问 Repository/SQL。
5. 语音先转成用户可见文字，再进入 Agent。
6. 食物图片和身体照片是业务附件，不由模型记忆代替。
7. AI 创建训练计划必须保存为 V2 正式计划。
8. AI 修改计划不能重写历史训练事实。
9. AI 导入必须先预览再批量写入。
10. “任意格式导入”是尽可能理解，不代表无法识别的数据也强行猜测。
11. 数据导出复用 V1.2 统一能力。
12. 用户实时业务数据优先于 RAG 和 Memory。
13. 高影响、批量和不确定操作必须确认。
14. 重试不能产生重复写入。
15. AI 服务异常不能损坏基础业务数据。

## 二十二、最终验收标准

### 1. 首页统一入口

- 用户登录 Dashboard 即可看到 AI 输入；
- 支持文字；
- 支持语音转文字；
- 支持附件；
- 传统页面仍可正常使用。

### 2. 自然语言饮食录入

- 可从一句话提取餐次、食品、重量；
- 食品匹配正确；
- 歧义会询问；
- 调用真实饮食业务能力；
- Dashboard 营养同步变化；
- 上传的食物图片能与记录关联。

### 3. 身体数据录入

- 可一句话记录体重/体脂/围度；
- 可关联进度照片；
- 重复日期不会静默覆盖。

### 4. 训练记录

- 能从自然语言形成实际训练组记录；
- 实际训练事实不被计划目标覆盖。

### 5. AI 训练计划

- 能根据用户约束生成结构化计划；
- 用户能多轮修改；
- 确认后正式保存到训练计划模块；
- 手动页面可继续编辑；
- AI 后续可再次读取并修改同一计划。

### 6. AI 导入

至少验证：

- CSV/XLSX；
- 文本；
- 文档/PDF；
- 截图/图片；

能够进入“识别 → 映射 → 预览 → 确认 → 导入 → 报告”的统一流程。

低置信度数据不得未经确认直接进入正式历史。

### 7. AI 导出

用户可以直接说：

> “导出最近三个月体重、每日营养和饮食图片。”

系统正确创建导出任务，并最终给出包含对应图片的数据包入口。

### 8. Memory

能理解“刚才那个食品/动作/计划”，但实时数据重新查询业务系统。

### 9. RAG 融合

回答可以同时使用用户实时数据和审核知识，并展示来源。

### 10. 幂等与可追踪

- SSE 中断重试不重复新增；
- 导入任务不重复执行；
- 任意一次 Agent 请求可定位到结构化意图和 Tool 调用结果。

## 二十三、技术约束（简版）

- LangChain4j 承担 Agent / Tool Calling 集成；
- Structured Output 使用明确 Schema；
- Redis 用于短期 Conversation Memory、Pending Action 等短期状态；
- MySQL 保存结构化业务事实；
- 对象存储保存用户上传图片/文件；
- RAG 使用独立检索能力；
- AI Chat 使用 SSE 流式响应；
- Speech-to-Text 只作为输入层；
- 导入解析和导出任务应复用现有业务 Service，不能直接绕过业务层。
