# Fitness Nutrition Platform — PRD V1.1：快速记录

## 一、版本概述

V1 已经能够准确记录饮食，但高频健身用户往往每天反复吃相同食品。如果每次都必须“搜索 → 打开详情 → 输入重量 → 选择餐次 → 保存”，长期使用成本仍然偏高。

V1.1 的目标不是增加新的营养逻辑，而是围绕“重复饮食”优化记录效率，让常见场景尽可能在 2～3 次核心操作内完成。

## 二、用户核心问题

- 我每天都吃鸡胸肉、米饭、鸡蛋，为什么还要天天搜索？
- 我今天早餐和昨天几乎一样，能不能直接复制？
- 我经常吃的食品能不能固定在首页？
- 食品库没有我常买的食品怎么办？
- 一顿饭有 4～5 个食品，能不能一次一起保存？

## 三、版本目标

1. 高频食品无需重复搜索；
2. 重复餐次可快速复制；
3. 用户可维护个人收藏；
4. 系统可根据历史行为展示最近和常吃食品；
5. 用户可创建只属于自己的食品；
6. 支持一次添加多个食品形成一餐；
7. 所有快捷能力最终仍落到 V1 的同一套饮食记录和营养快照规则。

## 四、功能范围

- 最近吃过；
- 常吃食品；
- 收藏食品；
- 复制上一餐；
- 复制昨天某一餐；
- 复制昨天全部；
- 自定义食品；
- 一次添加多个食品；
- 快捷记录入口重构。

本版本仍不包含：复杂单位换算、条码扫描、菜谱/复合餐、AI 自然语言录入。

## 五、Dashboard 快捷记录区

### 1. 功能定位

在 Dashboard “添加饮食”附近提供高频入口，减少用户进入完整食品搜索页的次数。

### 2. 快捷入口

建议包含：

- 最近吃过；
- 常吃；
- 收藏；
- 复制上一餐；
- 复制昨天；
- 添加多个食品。

入口数量较多时允许折叠到“快速记录”面板，避免 Dashboard 过于拥挤。

### 3. 快捷卡片展示

食品卡片可展示：

- 食品名称；
- 上一次记录重量；
- 上一次餐次；
- 每 100g 热量或上次实际热量；
- 收藏状态；
- “按上次重量添加”快捷按钮。

## 六、最近吃过

### 1. 定义

按用户最近实际记录时间倒序展示最近使用过的食品。

### 2. 展示规则

- 同一食品出现多次时默认只展示一张卡片；
- 显示最近一次使用信息；
- 默认展示最近 10～20 个，可分页或“查看更多”；
- 已停用食品仍可在历史中看到，但不应作为可直接新增的快捷项。

### 3. 操作

- 点击食品：进入重量确认；
- 点击“按上次重量添加”：自动带出上次重量和餐次，用户确认后保存；
- 可从最近列表加入收藏。

### 4. 空状态

新用户没有历史时展示：

> “记录几次饮食后，这里会出现你最近吃过的食品。”

## 七、常吃食品

### 1. 定义

基于最近一段时间的实际饮食频次，展示用户最常记录的食品。

### 2. 产品规则

- 常吃由系统自动计算，不要求用户手动维护；
- 统计窗口建议按近 30 天或近若干次记录；
- 排名以实际记录次数为主；
- 同频时可按最近使用时间排序；
- 对已停用食品不提供新增快捷操作。

### 3. 用户体验

系统需要让用户理解“常吃”是自动统计，而不是收藏：

- 收藏 = 用户主动标记；
- 常吃 = 系统根据行为计算。

## 八、收藏食品

### 1. 功能定位

用户手动固定自己常用但不一定近期高频的食品。

### 2. 收藏入口

- 食品搜索列表；
- 食品详情；
- 最近吃过；
- 常吃食品。

### 3. 收藏列表

展示：

- 食品名称；
- 分类；
- 标准营养；
- 最近记录情况（可选）；
- 取消收藏；
- 快速添加。

### 4. 规则

- 同一用户不可重复收藏同一食品；
- 取消收藏不影响历史饮食记录；
- 食品被停用后可显示“已停用”，但新增按钮不可用。

## 九、复制饮食

### 1. 复制上一餐

#### 定义

找到用户距离当前时间最近的一次已完成餐次，将该餐次中的食品复制到当前目标日期/餐次。

#### 复制前确认

弹窗展示：

- 来源日期；
- 来源餐次；
- 食品列表；
- 每项重量；
- 预计复制的总热量。

用户可：

- 全部复制；
- 取消某些食品后复制；
- 修改目标餐次。

### 2. 复制昨天某餐

用户选择：

- 早餐；
- 午餐；
- 晚餐；
- 加餐。

系统展示昨天该餐食品列表并允许确认后复制。

### 3. 复制昨天全部

#### 功能定位

适合饮食计划高度固定的用户，一次复制昨天所有餐次。

#### 确认信息

- 昨天总记录数；
- 总热量与宏量营养；
- 按餐次分组的食品；
- 目标日期默认为今天。

#### 规则

- 复制产生的是新的饮食记录，不与昨天记录共享可变状态；
- 新记录应保存当前复制时采用的历史食品快照；
- 若来源食品后来停用，系统应提示该项不可直接复制或要求用户重新选择；
- 整次复制应避免网络重试造成整批重复。

## 十、多食品一次添加

### 1. 使用场景

用户记录一顿包含多种食品的午餐：米饭、鸡胸肉、西兰花、鸡蛋。

### 2. 页面结构

同一页面允许添加多行食品：

| 字段 | 说明 |
| --- | --- |
| 食品 | 搜索并选择 |
| 重量 | 每个食品单独填写 |
| 营养预览 | 每行即时显示 |
| 操作 | 修改 / 删除该行 |

页面底部汇总：

- 总热量；
- 总蛋白质；
- 总脂肪；
- 总碳水；
- 餐次；
- 日期。

### 3. 保存规则

- 用户一次确认；
- 每个食品仍保存为独立饮食记录，便于后续单独编辑；
- 某一食品无效时，需要明确整批失败还是部分成功，V1.1 推荐整批校验后再保存，避免用户难以理解部分成功状态；
- 重复请求不得整批重复创建。

## 十一、自定义食品

### 1. 功能定位

解决公共食品库无法覆盖品牌食品、家庭食品和用户长期固定食品的问题。

### 2. 创建字段

- 食品名称；
- 每 100g 热量；
- 蛋白质；
- 脂肪；
- 碳水；
- 品牌/备注（可选）。

### 3. 权限规则

- 默认仅创建者自己可见；
- 普通用户不能把个人食品直接发布为公共食品；
- 管理员公共食品与用户自定义食品在 UI 上应有明确来源标识。

### 4. 编辑规则

- 用户可修改自定义食品的当前标准；
- 修改不影响既有历史记录；
- 删除/停用自定义食品不应破坏历史记录。

## 十二、快捷记录搜索体验

食品搜索页增加：

- 最近搜索（可选）；
- 最近吃过推荐；
- 收藏优先入口；
- 清晰区分公共食品与自定义食品。

搜索无结果时提供：

> “没有找到？创建自定义食品”

## 十三、关键业务规则

1. 所有快捷功能最终都复用 V1 的饮食记录规则。
2. 复制不是“引用旧记录”，而是创建新的记录事实。
3. 最近/常吃等推荐结果不能绕过食品有效状态校验。
4. 自定义食品修改不能污染历史。
5. 多食品提交需要保证用户理解成功/失败边界。
6. 系统自动统计的“常吃”不应冒充用户主动偏好。

## 十四、异常与空状态

| 场景 | 系统行为 |
| --- | --- |
| 没有最近记录 | 展示引导文案 |
| 没有收藏 | 引导去食品库收藏 |
| 昨天某餐为空 | 提示“昨天该餐没有可复制记录” |
| 复制项包含已停用食品 | 标记不可复制并要求处理 |
| 多食品中某项重量非法 | 不提交整批，定位到具体行 |
| 自定义食品营养值非法 | 阻止保存 |
| 批量保存网络超时 | 支持安全重试，不重复新增 |

## 十五、验收标准

- 最近吃过排序正确；
- 常吃统计与近阶段真实记录一致；
- 收藏/取消收藏即时生效；
- 可复制上一餐、昨天单餐和昨天全部；
- 复制不会修改来源记录；
- 多食品一次提交后 Dashboard 正确汇总；
- 自定义食品可新增、编辑、停用且历史不受影响；
- 高频用户常见食品记录可在 2～3 次核心操作内完成。

## 十六、技术约束（简版）

- 优先复用 V1 数据模型与业务服务；
- 最近/常吃可先通过历史记录计算，不要求提前建设复杂推荐系统；
- 收藏与自定义食品需要用户级数据隔离；
- 批量写入需要保持一致的幂等与事务语义。
