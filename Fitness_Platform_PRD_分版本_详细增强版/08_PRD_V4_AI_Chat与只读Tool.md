# Fitness Nutrition Platform — PRD V4：首页 AI Chat、语音输入与只读业务 Tool

## 一、版本概述

V4 是平台第一次正式引入 AI。

本版本不急于让 AI 修改业务数据，而是先建立未来整个产品的统一自然语言入口：用户打开 Dashboard 首页即可看到 AI 输入框，可以直接打字，也可以语音转文字，然后询问自己的真实饮食、身体和训练数据。

V4 的核心目标不是“做一个聊天机器人”，而是验证以下产品形态：

> 用户不需要先找到某个统计页面，也可以直接问：“我今天还差多少蛋白质？”、“最近一个月体重怎么样？”、“我上次卧推做多少？”；AI 通过系统已有业务能力查询真实数据后回答。

V4 严格限制为**只读**。写入饮食、体重、训练计划、历史数据导入等操作在 V5 Fitness Agent 开放。

## 二、用户核心问题

- 我能不能打开首页直接问，而不是到处找页面？
- 我不想打字的时候，能不能直接说话？
- “我今天还差多少蛋白质？”AI 能不能直接查我的真实数据？
- “我最近 30 天体重变化怎么样？”能不能直接告诉我？
- “我上次卧推多少？”能不能从训练记录里查？
- 连续问“那上周呢”“刚才那个动作呢”时，AI 能不能理解上下文？

## 三、版本目标

1. Dashboard 首页提供固定可见的 AI 输入区域；
2. 支持文字输入；
3. 支持语音转文字输入；
4. AI 能识别业务查询意图并调用只读 Tool；
5. 用户事实必须来自真实业务数据；
6. 支持短期会话上下文；
7. 支持 SSE 流式反馈；
8. 支持最近会话历史；
9. 不开放任何会真正修改用户业务数据的 AI 写操作；
10. 为 V5 “一句话完成业务操作”建立相同的首页交互入口。

## 四、产品入口

### 1. Dashboard 首页 AI 输入区

用户登录后进入 Dashboard，在核心数据卡片附近显示 AI 输入区。

推荐视觉结构：

```text
今天有什么需要我帮你？
[ 说说你想记录、查询或了解的内容…… ] [麦克风] [发送]

快捷问题：
[今天还差多少蛋白质？]
[最近7天体重变化]
[上次卧推记录]
```

V4 由于只读，placeholder 可以根据能力提示为：

> “问问今天摄入、身体趋势或训练记录……”

V5 再升级为：

> “说说你吃了什么、练了什么，或者让我帮你安排计划……”

### 2. 独立 AI 页面

Dashboard 首页只保留轻量入口和最近对话。

用户点击“展开对话”后进入完整 AI 页面，支持：

- 查看消息历史；
- 查看数据结果卡片；
- 新建会话；
- 切换最近会话；
- 停止生成；
- 重新发送。

### 3. 传统页面继续保留

AI 不是唯一入口。

饮食、身体、训练等传统页面继续存在，便于：

- 查看完整列表；
- 手动编辑；
- 校对数据；
- 处理复杂表单；
- AI 不可用时正常使用平台。

## 五、文字输入

### 1. 基本操作

- 输入文字；
- Enter/发送按钮提交；
- 多行文本支持；
- 输入为空时不可发送；
- 生成过程中允许停止。

### 2. 快捷问题

根据用户当前数据动态展示建议问题，例如：

- “我今天还差多少热量？”
- “总结最近 7 天饮食。”
- “这周平均体重多少？”
- “我上次腿训练是什么时候？”

快捷问题只用于帮助用户理解能力，不应强制使用。

## 六、语音转文字输入

### 1. 产品定位

语音是输入方式，不是独立业务逻辑。

标准流程：

```text
用户点击麦克风
→ 开始说话
→ 系统转为文字
→ 用户看到转写结果
→ 用户可修改
→ 用户发送
→ AI 按普通文本处理
```

### 2. 为什么先转文字再发送

健身记录包含大量数字、单位和动作名，例如：

- 72.4kg；
- 300g 米饭；
- 卧推 80kg × 8；
- RPE 8；

语音识别可能出现数字和专有名词错误，因此 V4/V5 默认应让用户看到文字结果。

### 3. 语音状态

页面需展示：

- 未开始；
- 正在录音；
- 正在转写；
- 转写完成；
- 转写失败。

### 4. 操作

- 开始录音；
- 停止；
- 取消；
- 转写后编辑文字；
- 重新录音；
- 发送。

### 5. 权限异常

如果浏览器/设备没有麦克风权限：

- 提示用户开启权限；
- 不影响文字输入；
- 不反复弹窗打断正常操作。

### 6. 隐私

产品默认只需要获得转写结果用于本次输入。

是否保留原始音频应有明确策略；若没有实际业务需求，不建议默认长期保存用户原始语音。

## 七、AI 可查询的业务能力

### 1. 用户与目标

可查询：

- 当前用户基础资料；
- 当前营养目标；
- 指定日期营养目标；
- 目标历史。

### 2. 饮食

可查询：

- 今日饮食；
- 指定日期饮食；
- 每日营养汇总；
- 按餐次记录；
- 食品搜索与详情；
- 最近/常吃信息（如已上线）。

### 3. 身体数据

可查询：

- 最新体重；
- 指定日期范围身体数据；
- 体重/体脂/围度趋势；
- BMI/BMR/TDEE 等已有派生指标。

AI 不需要读取身体照片内容来做评价；如未来支持视觉能力应单独定义。

### 4. 训练

可查询：

- 当前训练计划；
- 今日训练；
- 训练历史；
- 某动作历史；
- 最近一次训练数据；
- 已有训练统计。

### 5. 数据导出状态

如 V1.2 已上线，可查询：

- 最近导出任务；
- 某次导出是否完成；
- 当前可导出的数据范围说明。

V4 不主动创建导出任务，V5 开放自然语言触发导出。

## 八、只读 Tool 产品原则

1. AI 不直接读取数据库；
2. AI 不自行构造任意 SQL；
3. 所有数据通过稳定业务能力读取；
4. 权限与普通页面一致；
5. 查询不到就如实回答没有数据；
6. 会话 Memory 中的旧数据不能替代实时查询。

例如用户问：

> “我今天吃了多少？”

AI 必须查询今天当前记录。

不能因为 10 分钟前的聊天里显示 1600 kcal，就在用户新增晚餐后仍回答 1600 kcal。

## 九、只读边界

用户如果在 V4 说：

> “午饭吃了 300g 米饭，帮我记一下。”

系统应：

- 识别用户想记录饮食；
- 明确说明当前 AI 版本暂不执行写入；
- 提供“去记录饮食”快捷入口；
- 可将已识别的文字保留，减少用户重复输入（可选）。

同理以下请求 V4 不执行：

- “今天体重 72.3kg，记一下。”
- “把周三训练改周四。”
- “给我创建一个训练计划。”
- “把这个 Excel 导进来。”

## 十、短期会话上下文

### 1. 使用场景

```text
用户：我今天午餐吃了多少？
AI：午餐共……
用户：那它占我目标多少？
```

第二句需要理解“它”。

### 2. 可记忆内容

- 最近若干轮消息；
- 最近引用日期；
- 最近食品/动作实体；
- 最近查询结果摘要；
- 当前话题。

### 3. 不能依赖 Memory 的内容

- 当前总摄入；
- 当前体重最新值；
- 当前计划是否被修改；
- 任何可能变化的业务事实。

这些内容再次被问到时重新查询业务系统。

## 十一、SSE 流式体验

### 1. 用户可见状态

一次回答可以依次展示：

- 正在理解你的问题；
- 正在查询今日营养；
- 正在读取训练记录；
- 正在生成回答；
- 完成。

### 2. 页面表现

- 文字逐步输出；
- 查询结果卡片可以先于完整文字出现；
- 用户可停止生成；
- 网络中断后允许重新发送。

### 3. 不展示模型内部推理

页面可以展示“正在查询体重趋势”，但不展示模型内部 Chain-of-Thought。

## 十二、数据结果卡片

对于高频结构化查询，除了文字回答，可展示轻量卡片。

### 1. 今日营养卡

- 已摄入；
- 目标；
- 剩余；
- 蛋白质/脂肪/碳水。

### 2. 身体趋势卡

- 最新体重；
- 7/30 天变化；
- 迷你趋势图。

### 3. 训练结果卡

- 最近训练日期；
- 动作；
- 主要组数据；
- 本次训练入口。

卡片点击可进入对应传统业务页面。

## 十三、权限与隐私

- AI 只能查询当前登录用户有权访问的数据；
- 不允许模型指定任意 userId 越权查询；
- V3 教练数据继续遵守授权关系；
- 密码、JWT、Secret 不进入模型上下文；
- 原始语音不应在没有产品必要性的情况下长期保存；
- 会话记录应有清晰隐私策略。

## 十四、异常与降级

| 场景 | 系统行为 |
| --- | --- |
| AI 服务不可用 | 基础业务页面仍可正常使用 |
| Tool 查询失败 | 明确说明对应数据暂时获取失败 |
| 没有业务数据 | 如实说明没有记录 |
| Memory 丢失 | 当前明确问题仍可继续，新指代要求重新说明 |
| SSE 中断 | 可重新发送 |
| 麦克风无权限 | 提示权限，继续支持文字输入 |
| 语音转写失败 | 可重新录音或手动输入 |
| 用户要求写入 | 不执行，提供业务页面入口 |

## 十五、业务规则与约束

1. Dashboard AI 输入框是未来统一入口，从 V4 开始建立用户习惯。
2. V4 只读，不因“用户说得很明确”而偷偷执行写操作。
3. 语音先转写为可见文字，再进入 AI 理解流程。
4. AI 查询用户事实必须调用业务 Tool。
5. Memory 用于理解，不是事实数据库。
6. AI 故障不能阻塞原有功能。
7. V5 必须复用同一首页 AI 交互，而不是另做一套孤立 Agent 页面。

## 十六、验收场景

### 场景 A：首页文字查询

用户打开 Dashboard 直接输入：

> “我今天还差多少蛋白质？”

系统查询真实数据并返回结果，不要求先进入 AI 独立页面。

### 场景 B：语音查询

用户点击麦克风说：

> “帮我看看最近一个月体重变化。”

系统：

- 完成语音转文字；
- 展示转写结果；
- 用户发送；
- 查询身体数据；
- 返回趋势。

### 场景 C：多轮上下文

```text
用户：我上次卧推多少？
AI：……
用户：那再上一次呢？
```

AI 能理解“再上一次”并再次查询正确数据。

### 场景 D：拒绝写操作

用户说：

> “早餐吃了两个鸡蛋，帮我记。”

V4 不新增记录，明确提示写操作将在后续 Agent 版本开放，并提供快速记录入口。

## 十七、技术约束（简版）

- LangChain4j 负责 AI 与 Tool Calling 集成；
- 业务事实仍由 Java Service 提供；
- Redis 可保存短期会话上下文；
- AI 响应使用 SSE 流式输出；
- 语音采用 Speech-to-Text 能力，业务层接收转写文本；
- 不在 PRD 固定具体语音服务供应商。
