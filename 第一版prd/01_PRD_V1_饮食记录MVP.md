# Fitness Nutrition Platform — PRD V1：饮食记录 MVP

## 一、项目概述

V1 是平台的业务基础版本，面向普通健身用户提供轻量、快速、准确的每日饮食与宏量营养素记录能力。

用户最核心的问题不是“让 AI 帮我制定复杂计划”，而是：

- 我今天到底吃了多少？
- 蛋白质、脂肪、碳水分别吃了多少？
- 距离今天的目标还差多少？
- 昨天、前天或某一天到底吃了什么？
- 食品库后来修改后，我以前的记录还能不能保持原来的结果？

V1 围绕“设定目标 → 搜索食品 → 输入重量 → 保存记录 → 查看今日完成情况 → 查看历史”建立完整闭环。

## 二、用户角色与核心目标

### 1. 普通用户 USER

核心目标：

- 注册并登录个人账户；
- 设置每日热量与三大营养素目标；
- 查询食品并快速记录实际摄入；
- 查看当日营养汇总、剩余目标和餐次明细；
- 查询、编辑和删除历史记录；
- 确保自己的数据与其他用户严格隔离。

### 2. 管理员 ADMIN

核心目标：

- 管理食品分类和食品基础数据；
- 维护食品标准营养信息；
- 将错误、下架或暂不可用食品设置为停用；
- 确保食品库调整不会影响用户已经发生的历史记录。

### 3. 本版本不包含角色

- 真人教练；
- AI Agent；
- 社区运营角色。

## 三、V1 核心目标与成功标准

V1 上线后至少满足：

1. 新用户可以完成注册、登录、设置营养目标并进入 Dashboard。
2. 用户可以在 30 秒内完成一次常规食品记录。
3. 用户输入食品和重量后，系统展示的营养结果一致、可复现。
4. 用户可以按早餐、午餐、晚餐、加餐查看当日记录。
5. 用户可以看到热量、蛋白质、脂肪、碳水的已摄入、目标、剩余和完成度。
6. 用户可以查看任意允许范围内的历史日期。
7. 管理员修改食品营养信息后，不影响已有历史记录。
8. 用户修改历史记录重量时，仍按当时保存的营养口径重新计算。
9. 所有用户资源必须按当前登录用户隔离。
10. 重复提交不能产生明显重复记录。

## 五、系统基础功能

### 1. 用户注册

#### 功能定位

为新用户建立独立账户，是所有个人业务数据的身份基础。

#### 注册字段

- Email：必填；
- 密码：必填；
- 确认密码：必填；
- 昵称：可选或注册后补充；
- 用户时区：前端自动检测并允许后续修改。

#### 业务规则

- Email 必须符合合法格式；
- Email 去除首尾空格并按统一大小写规则处理；
- Email 不允许重复注册；
- 密码不得明文保存；
- 两次密码输入必须一致；
- 注册成功后可跳转登录页或直接进入已登录状态，具体交互保持统一；
- V1 不强制邮件验证。

#### 异常与提示

- Email 已存在：提示“该邮箱已注册”；
- Email 格式错误：字段下方即时提示；
- 密码不符合规则：明确说明长度要求；
- 网络异常：保留用户已填写内容，允许重新提交。

### 2. 用户登录

#### 登录字段

- Email；
- Password。

#### 登录行为

- 登录成功进入 Dashboard；
- 登录失败提示账号或密码错误，不暴露账户是否存在等过多安全信息；
- 被禁用账户不可登录；
- 已登录用户刷新页面后保持有效登录状态；
- 退出登录后回到登录页，受保护页面不可继续访问。

### 3. 用户资料与时区

#### 页面信息

- Email；
- 昵称；
- 当前时区；
- 账号状态；
- 注册时间（可选展示）。

#### 时区规则

- 使用标准时区名称，如 `Asia/Shanghai`；
- “今天”由用户当前时区决定；
- 用户修改时区后，不自动移动已经保存的历史业务日期；
- 系统需要明确区分“用户认为是哪一天吃的”和“系统实际创建时间”。

## 六、营养目标模块

### 1. 功能定位

用户为某个时间阶段设置每日目标，用于 Dashboard 计算完成度和剩余量。

### 2. 目标字段

- 每日热量目标 kcal；
- 蛋白质 g；
- 脂肪 g；
- 碳水化合物 g；
- 生效日期。

### 3. 当前目标展示

页面应显示：

- 当前目标是否存在；
- 当前热量目标；
- 当前蛋白质目标；
- 当前脂肪目标；
- 当前碳水目标；
- 当前目标开始生效日期。

### 4. 目标创建与切换

用户第一次设置目标时直接创建当前目标。

用户后续调整目标时：

- 新目标从用户选择的生效日期开始；
- 旧目标在新目标开始前结束；
- 历史日期查询仍使用当时有效的旧目标；
- 同一天最多只能存在一组有效目标；
- 不允许出现时间区间重叠导致同一天命中多组目标。

### 5. 目标历史

历史列表至少展示：

- 生效开始日期；
- 结束日期；
- 热量；
- 蛋白质；
- 脂肪；
- 碳水；
- 是否当前目标。

### 6. 校验与异常

- 热量必须大于 0；
- 三大营养素不能为负数；
- 极端不合理数值应拒绝并提示；
- 未设置目标时仍允许记录饮食，但 Dashboard 不展示完成百分比和剩余目标；
- V1 不提供随意删除历史目标的能力。

## 七、食品库模块

### 1. 功能定位

为饮食记录提供标准化食品实体与当前标准营养数据。

### 2. 食品搜索页面

#### 页面入口

- Dashboard “添加饮食”；
- 主导航“食品库”。

#### 搜索能力

- 按食品名称模糊搜索；
- 支持中文名称；
- 英文名称可选支持；
- 可按食品分类筛选；
- 仅向普通用户展示可用食品。

#### 食品列表字段

- 食品名称；
- 分类；
- 每 100g 热量；
- 每 100g 蛋白质；
- 每 100g 脂肪；
- 每 100g 碳水；
- 状态仅在管理员页面展示。

#### 空状态

- 无关键词时可展示默认食品或提示搜索；
- 搜索无结果时展示“暂无匹配食品”；
- 不自动猜测相似食品并直接替用户选择。

### 3. 食品详情

展示：

- 食品名称；
- 英文名（如有）；
- 分类；
- 描述（如有）；
- 标准营养口径：每 100g；
- 热量、蛋白质、脂肪、碳水；
- 数据来源说明（如有）。

### 4. 食品状态规则

- ACTIVE：普通用户可搜索、查看并新增记录；
- INACTIVE：普通用户不可用于新增记录；
- 已经基于该食品产生的历史饮食记录必须继续可展示；
- 管理员在用户提交前刚好停用食品时，以服务端最终状态为准。

## 八、饮食记录模块

### 1. 新增饮食记录

#### 入口

- Dashboard “添加饮食”；
- 食品详情“记录此食品”。

#### 录入字段

- 食品：必填；
- 食用重量 g：必填；
- 餐次：早餐/午餐/晚餐/加餐；
- 记录日期：默认今天，可在允许范围内修改。

#### 即时预览

用户输入重量后，页面即时展示预计摄入：

- calories；
- protein；
- fat；
- carbohydrate。

预览仅用于用户确认，最终保存结果应由后端按当前食品标准重新确认。

#### 保存成功

保存后：

- 返回 Dashboard 或显示成功反馈；
- 对应餐次立即出现新记录；
- 当日汇总立即变化；
- 剩余目标和完成度立即变化。

### 2. 营养计算口径

V1 统一使用“每 100g”作为食品基础营养口径。

实际摄入 = 每 100g 营养 × 实际重量 / 100。

营养数值需要保持十进制计算准确性，不因界面显示位数提前丢失精度。

### 3. 历史营养快照

这是 V1 的关键业务规则。

当一条饮食记录创建时，除关联食品外，还必须固化：

- 当时的食品名称；
- 当时每 100g 的热量、蛋白质、脂肪、碳水；
- 本次实际重量；
- 本次实际摄入结果。

目的：

- 管理员未来修改食品标准营养数据，不改变已经发生的历史；
- 用户以后查看某一天，看到的是当时记录的事实；
- 用户修改历史记录重量时，仍可按当时营养口径重新计算。

### 4. 编辑饮食记录

#### 可编辑项

- 重量；
- 餐次；
- 日期；
- 食品（如产品允许在编辑页更换）。

#### 修改重量

- 使用该记录保存的历史“每 100g 快照”重新计算；
- 不读取食品库今天最新的营养值。

#### 修改餐次

- 只改变早餐/午餐/晚餐/加餐归属；
- 营养值不变。

#### 修改日期

- 记录从原日期移出；
- 新日期增加该记录；
- 两天的 Dashboard/历史汇总都需要立即反映变化。

#### 修改食品

更换食品等同重新选择食品：

- 使用新食品当前营养信息；
- 创建新的营养快照；
- 页面需要明确提示“更换食品将按新食品当前营养重新计算”。

### 5. 删除饮食记录

- 删除前提供明确确认；
- 删除成功后从记录列表移除；
- 当日汇总立即刷新；
- V1 不提供用户侧回收站；
- 删除失败时保留页面上下文并提示重试。

### 6. 重复提交

用户连续点击保存、网络超时后重试等情况下，不应创建明显重复的同一次记录。

产品层要求：

- 客户端提交一次业务操作应带唯一请求标识；
- 同一请求重复到达时返回原有结果或明确提示已处理；
- 用户不需要理解技术细节。

## 九、Dashboard 模块

### 1. 功能定位

Dashboard 是用户日常使用频率最高的页面，用于回答“今天吃了多少、还差多少”。

### 2. 顶部信息

- 当前业务日期；
- 用户昵称；
- 当前目标状态；
- 添加饮食快捷入口。

### 3. 营养总览卡片

分别展示：

- 热量；
- 蛋白质；
- 脂肪；
- 碳水。

每项至少包含：

- 已摄入；
- 目标；
- 剩余；
- 完成百分比。

### 4. 超标展示

若已摄入超过目标：

- 剩余可以为负值；
- 页面应明确显示“超出 X”；
- 真实完成度可以超过 100%；
- 进度条视觉长度可以封顶，但数字不应伪造为 100%。

### 5. 餐次列表

按顺序展示：

- 早餐；
- 午餐；
- 晚餐；
- 加餐。

每条记录至少展示：

- 食品名称；
- 重量；
- 热量；
- 可进入编辑；
- 可删除。

### 6. Dashboard 空状态

#### 未设置目标

- 提示“尚未设置每日营养目标”；
- 提供“去设置”入口；
- 仍展示已摄入数据；
- 不展示虚假的完成率。

#### 当天没有记录

- 已摄入显示为 0；
- 各餐次展示空状态；
- 提供“添加第一条饮食记录”按钮。

## 十、历史记录模块

### 1. 功能定位

允许用户查看过去某一天的目标和实际饮食事实。

### 2. 日期查询

- 默认可从今天向过去切换；
- 提供日期选择器；
- 可快速返回今天；
- 日期范围应限制在合理区间，防止明显错误日期。

### 3. 历史页面展示

- 选中日期；
- 当天有效的营养目标；
- 当天实际摄入；
- 当天剩余；
- 完成度；
- 早餐/午餐/晚餐/加餐记录。

### 4. 历史事实规则

- 查询某一天目标时使用当天有效目标，不使用今天目标；
- 食品库今天的数据变化不能改写历史；
- 修改历史记录后，仅相关日期统计发生变化。

## 十一、管理员食品管理

### 1. 食品分类管理

管理员可：

- 查看分类列表；
- 新增分类；
- 修改分类名称和排序；
- 设置分类可用状态；
- 查看分类下食品数量（可选）。

业务规则：

- 分类名称不能为空；
- 已被食品使用的分类不建议直接物理删除；
- 分类停用后，普通用户不再作为可选筛选项展示，但历史数据不受影响。

### 2. 食品管理列表

#### 搜索与筛选

- 食品名称关键词；
- 分类；
- 状态 ACTIVE / INACTIVE；
- 分页。

#### 列表字段

- ID；
- 食品名称；
- 分类；
- 每 100g 热量；
- 蛋白质；
- 脂肪；
- 碳水；
- 状态；
- 最近更新时间；
- 操作。

### 3. 新增/编辑食品

字段：

- 中文名称；
- 英文名称（可选）；
- 分类；
- 描述；
- 每 100g 热量；
- 蛋白质；
- 脂肪；
- 碳水；
- 数据来源；
- 状态。

校验：

- 名称 trim 后不能为空；
- 营养值不能为负；
- 不强制食品名称全局唯一，因为同名不同品牌/来源可能合理存在；
- 修改营养值后，只影响未来新创建的记录。

### 4. 停用食品

- 管理员可将食品从 ACTIVE 切换为 INACTIVE；
- 停用不等于删除；
- 停用后普通用户不能新增该食品；
- 历史记录继续显示保存的名称和营养快照。

## 十二、关键业务流程

### 1. 首次使用

```text
注册
→ 登录
→ 系统发现没有当前营养目标
→ 引导设置热量 / 蛋白质 / 脂肪 / 碳水目标
→ 保存
→ 进入 Dashboard
```

### 2. 记录午餐

```text
Dashboard
→ 添加饮食
→ 搜索“米饭”
→ 选择食品
→ 输入 400g
→ 查看即时营养预览
→ 选择午餐
→ 保存
→ Dashboard 汇总刷新
```

### 3. 查看昨天

```text
历史记录
→ 选择昨天
→ 加载昨天有效目标
→ 加载昨天饮食记录
→ 显示昨天摄入 / 剩余 / 完成度
```

### 4. 修改历史重量

```text
打开历史记录
→ 选择某条食品
→ 400g 改为 300g
→ 按该记录历史营养快照重新计算
→ 保存
→ 当天汇总刷新
```

## 十三、业务规则与约束

1. 客户端不得直接决定最终营养结果，服务端需按可信食品数据重新确认。
2. 历史记录必须独立于食品当前数据。
3. 当前用户身份来自登录上下文，不接受前端随意指定其他 userId。
4. 查询、编辑、删除个人记录时必须验证记录属于当前用户。
5. 记录日期按用户业务时区理解。
6. 已经发生的业务日期不随用户后来修改时区自动迁移。
7. 未设置目标不影响记录饮食，但目标相关字段应为空而不是假值。
8. 数据删除或修改后，Dashboard 与历史汇总应立即一致。

## 十四、异常与边界场景

| 场景 | 系统行为 |
| --- | --- |
| 输入 0g | 禁止提交 |
| 输入负数 | 禁止提交 |
| 输入极端大重量 | 拒绝并提示超出允许范围 |
| 食品不存在 | 提示食品不存在或已失效 |
| 食品提交瞬间被管理员停用 | 保存失败并提示重新选择 |
| 当天无目标 | 可记录，目标/完成率为空 |
| 当天无记录 | consumed=0，展示空状态 |
| 食品后来被停用 | 历史正常显示 |
| 食品营养后来修改 | 历史不变 |
| 修改历史重量 | 按历史快照重算 |
| 删除记录 | 当日统计立即减少 |
| 网络超时 | 保留输入，允许安全重试 |
| 重复点击保存 | 不产生多条相同业务请求记录 |
| 用户访问他人记录 | 不展示数据，返回无权限/不存在体验 |
| 目标时间区间冲突 | 阻止保存并提示调整生效日期 |

## 十五、权限与安全需求

- 普通用户只能访问自己的个人数据；
- ADMIN 可以维护食品/分类，但不能默认读取任意用户隐私数据；
- `/admin` 类功能仅管理员可访问；
- 密码等敏感信息不得明文存储或回传；
- 所有新增、修改、删除操作必须进行服务端校验；
- 对重复提交提供业务幂等保护；
- 关键异常需有可定位日志，但不得记录密码和 Token。

## 十六、非功能性需求

### 1. 易用性

- 高频记录路径尽量短；
- 表单字段有清晰单位；
- 保存、删除、切换目标等关键操作有明确成功/失败反馈；
- 空状态应给出下一步操作，而不是只显示空白页面。

### 2. 一致性

- 列表数据、Dashboard 汇总、历史汇总必须使用一致口径；
- 同一次新增/修改/删除完成后，用户刷新或重新进入页面应得到同样结果。

### 3. 性能体验

- 普通食品搜索、Dashboard、单日历史查询应在正常网络下快速返回；
- V1 不为了未来规模提前引入复杂离线统计，优先保证简单可靠。

### 4. 可追溯性

- 用户历史记录保留当时的食品与营养事实；
- 管理员食品调整不应污染历史。

## 十七、验收标准

### 1. 账户

- 可注册、登录、退出；
- 重复邮箱不可注册；
- 未登录不可访问受保护页面。

### 2. 营养目标

- 可创建第一组目标；
- 可从新日期切换目标；
- 查询历史日期得到当时目标；
- 不存在同一天两组有效目标。

### 3. 食品

- 可按名称搜索；
- 可查看每 100g 营养；
- 普通用户看不到 INACTIVE 食品作为新增候选。

### 4. 饮食记录

- 创建后 Dashboard 立即增加；
- 编辑重量后按历史快照重算；
- 删除后立即减少；
- 餐次和日期调整后归属正确；
- 重复提交不会生成重复业务记录。

### 5. 历史快照

验收用例：

```text
先记录米饭 100g = 116 kcal
→ 管理员把米饭修改为 130 kcal / 100g
→ 再查看原历史记录
→ 仍显示 116 kcal
```

### 6. 权限

用户 A 不得通过修改 URL、记录 ID 或请求参数读取/修改用户 B 的饮食、目标和资料。

## 十八、技术约束（简版）

- 后端：Java 21 + Spring Boot 3；
- 登录与权限：Spring Security + JWT；
- 数据库：MySQL 8.x；
- 营养计算使用十进制定点计算，避免普通浮点误差；
- V1 Redis 非强依赖；
- AI/LangChain4j/RAG 不进入 V1。
